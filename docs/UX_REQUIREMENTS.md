# 阶段 7: 从用户角度细化流程需求

> 2026-08-09。以「苹果工程师的细节敏锐度」重走导入 → 配置 → 备料 → 阅读 → 删除全流程,
> 记录用户能感知的每一步要求。原则: 状态永远可视、失败永远可行动、边界永远有解释、
> 数据永远不静默丢。每条标注现状(已实现/缺口)与落点。

## 1. 导入原书

| # | 用户视角需求 | 现状 |
|---|---|---|
| 1.1 | 拖入或点选一本书, 立即有反馈("正在导入 N 本…") | ✅ toast |
| 1.2 | 同一文件重复导入: 不新增卡片, 明确提示"之前已导入, 可直接创建译本" | ✅ 阶段2 skipped 文案 |
| 1.3 | 导入成功后提示下一步是什么("已导入原书, 下一步: 为原书创建译本") | ✅ 阶段2 notice/toast |
| 1.4 | 导入只登记原书, 不自动开始处理, 不假装"已加入处理队列" | ✅ 阶段2 文案修正 |
| 1.5 | 原书卡上**没有**"打开阅读"按钮(原书不可读) | ✅ 阶段2 移除 |
| 1.6 | 原书卡显示格式/大小/导入时间(用户判断是不是导错了文件) | ⚠️ 缺口: 现只显示标题/档案/语言 |
| 1.7 | 快速连点"导入"两次只触发一次 | ✅ 阶段2 ImportDedup |

## 6. 已知缺口(阶段 7 排期候选)

- **1.6 原书卡格式/大小/导入时间**: 需要后端 books 表加 size_bytes(或导入时读文件 metadata),
  前端 source 卡显示 "EPUB · 1.8 MB · 08-09 导入"。
- **2.4 模型四态统一展示**: 后端按 BOOK_WORKFLOW §2.2 返回统一状态(已扫描/已登记/可用/
  已绑定), 前端只渲染。
- **3.3 译本出现延迟**: 处理完成 → library-changed 事件目前只被 prep_view 消费; 让
  library_view 也监听 library-changed 即时刷新书库(比 5s 轮询快)。
- **prep_view "打开书籍"的 book_id 计算(F1)**: 前端按输出目录名重算 book_id, 与 Rust 规则
  不同步(lowercase 差异)。正确修法: job 完成后返回 edition_id, 前端直接用它打开, 不重算。
- **导航仍是四页签**: 完整设计交付确认 §10 item 3(三层导航)未落地, 见 ROADMAP 阶段6清单。
