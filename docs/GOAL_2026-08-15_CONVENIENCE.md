# 便利性/完整度需求挖掘(2026-08-15)

## 这份文档是什么

跟 2026-08-14 的"成熟度审计"(见 `ROADMAP.md`"成熟度审计"节)是两种不同性质的挖掘:

- 2026-08-14 那轮找的是**正确性/边界缺口**——按 CLAUDE.md 的五个维度(配置管理/
  外部系统集成/依赖交付/状态管理/错误反馈)逐域核对, 找"会出错但没处理"的地方。
- 这一轮找的是**便利性/完整度缺口**——不是"错了", 是"一个成熟产品这里通常会有,
  但这里没有"。起因: 用户实测书库页发现排序/卡片大小/生词发音都是这类"顺手的
  需求", 用户原话"这种需求我还是觉得应该是成熟度带出来的, 而不是我需要想到的"。

用 progate(deepseek-v4-pro)逐域深挖, 编排方(当前会话)只做范围框定和轻量复核,
**这一轮不改代码**, 只产出带方案选项和取舍权重的报告, 由用户最后拍板选哪些做。

## 怎么读这份文档

每条挖掘结果按这个格式:

```
### [域] 具体缺口标题

**方案选项**:
  - 方案 A(...): 优点/缺点/大致改动量
  - 方案 B(...): 优点/缺点/大致改动量
**建议权重**: 高/中/低(基于"用户实际会用到的频率"和"改动量"的粗略权衡, 仅供参考,
  不是编排方替用户做决定)
```

## 书库/封面

(范围: reader/views/library_view.js + reader/views/library/*.js + reader/styles/library.css。
2026-08-15 已加排序下拉 + 卡片大小切换、网格/列表视图跳过不做——这几点不复提, 只挖别的。)

### 书库/封面 搜索只匹配书名、不匹配作者

**现状**: `library_view.js` 第 197 行 `(b.title || b.id).toLowerCase().includes(q)` —— 搜索框只对书名/id 做
子串匹配。书名/作者已经在卡片上拆成两行显示(第 223-228 行, `AiduTitleCleanup.parseBookTitle` 拆出 `author`),
但作者值不进搜索索引。排序下拉 `_sortBooks`(第 405-431 行)也只有 recent/title/progress/added 四轴, 没有"作者"轴。
**对比**: 微信读书/Kindle/Calibre 都支持按作者搜到该作者全部书; "记得是村上春树那本、想不起书名"是极常见场景。
**方案选项**:
  - 方案 A(搜索补作者): 第 197 行把匹配范围从 `b.title` 扩到解析出的 `author`(需在 `_renderBooks` 里缓存解析结果)。改动 ~5 行, 立即见效。
  - 方案 B(再加作者排序): 排序下拉加"作者 A-Z"。改动也小, 但作者值来自文件名清洗, 可能不干净。
**建议权重**: 高(方案 A)—— 高频 + 改动极小。

### 书库/封面 "部分失败"的书卡只显示失败计数、没有跳转/重试入口

**现状**: `library_view.js` 第 252 行 `book.failed_count ? ... ${book.failed_count} 句失败` 把失败句数拼成一段
纯文本; 徽章 `partial` → "部分失败"(status.js 第 21 行)。真正的重试/详情(重试失败句、结构化失败详情、重跑范围)
都在 `prep_view.js`(第 283-287、367-369 行), 书库页没有通向它的入口——用户看到"3 句失败"得自己去"阅读准备"页找任务行。
**对比**: 成熟产品里"部分失败"卡片的失败计数通常是可点/带"重试"动作的, 或至少一键跳到失败详情。
**方案选项**:
  - 方案 A(失败计数变链接): 把"句失败"做成按钮, 点击跳 `#/prep` 并定位到对应任务。改动 ~10 行 + 一个路由 intent。
  - 方案 B(卡片直接带"重试失败句"): 复用 `AiduJobService.retryFailed`, 在 partial 卡上放重试按钮。改动 ~15 行, 书↔job 映射已有 path 匹配逻辑可复用(第 275-277 行)。
**建议权重**: 中(方案 A 更稳, B 更顺手但要多绕一层)。

### 书库/封面 没有批量操作(多选删除/导出)

**现状**: 删除只在 `_openBookMenu` 里单本触发(第 527-539 行), 每本要"点 ⋯ → 点删除 → 点确认"三步; 导出同样
单本(第 989-996 行)。整个文件没有"选择模式/多选"的任何状态或 DOM。
**对比**: 任何书库产品, 用户攒了几十本后要清理/迁移, 都会期望"勾选多本 → 一次删除/导出"。10 本时逐本操作已明显烦人。
**方案选项**:
  - 方案 A(卡片复选框 + 工具条批量删除/导出): 增加 `_selection` Set + 复选框/长按切换选择模式 + 工具条出现"删除 N 本"。改动中等(~40-60 行 + 样式), 覆盖面最大。
  - 方案 B(只做"全选当前筛选结果 + 批量删除"): 不做逐本勾选, 只给"删除当前筛选范围"。改动更小但粒度粗、误删风险高。
**建议权重**: 中高(方案 A)—— 高频且是"成熟度"硬指标, 但需后端支持批量删除(目前 `remove` 是单 id, library_service.js 第 23 行)。

### 书库/封面 删除没有撤销/回收站

**现状**: 第 530-537 行删除即调 `AiduLibraryService.remove(book.id, true)`(第二个参数 `deleteFiles=true` 连磁盘
一起删), 确认框文案"无法恢复"。删错只能重新导入 + 重新备料(可能几十分钟 TTS)。
**对比**: 成熟产品对高成本、不可逆的操作通常给"撤销"窗口(Google Drive 回收站, 或"已删除, 撤销"的 toast)。
**方案选项**:
  - 方案 A(软删除 + 撤销 toast): `remove(book.id, false)` 只删 DB 行不删磁盘, 弹出带"撤销"按钮的 toast(几秒内回滚)。改动 ~15 行 + toast 支持撤销按钮。
  - 方案 B(回收站页): 完整回收站。改动大, 不值。
**建议权重**: 中(方案 A)—— 数据丢失敏感 + 备料成本高, 但"撤销窗口"体验本身有取舍。

### 书库/封面 书名/作者不可编辑, 封面不能自定义

**现状**: 书名/作者完全由 `AiduTitleCleanup.parseBookTitle` 从文件名清洗而来(第 223 行), 清洗错了就永远错,
没有编辑入口; 封面只有"自动抽取 + 补封面"(第 553-567 行, 仅重跑抽取), 没有"自己选一张图当封面"或"移除封面回占位块"。
**对比**: Calibre/微信读书都允许改书名/作者元数据、自定义封面; 导入的 EPUB 文件名脏(如 `book_1.epub` 或 z-library 后缀)是常态。
**方案选项**:
  - 方案 A(书设置弹窗加"书名/作者"编辑字段): 复用已有 `_openBookSettings`(第 858-986 行), 加两个文本框, 存到 source 元数据。改动 ~30 行 + 一个 setTitle 后端命令。
  - 方案 B(自定义封面: 菜单加"更换封面"→ 选本地图): 需新增"写封面文件"后端命令 + 前端 pickFiles。改动中等。
**建议权重**: 中(方案 A 比 B 优先, 书名错误比封面缺失更痛)。

### 书库/封面 排序/卡片大小/筛选/译本展开等 UI 状态不跨会话持久化

**建议权重**: 低中(方案 A)—— 会用但频率低, 改动小所以性价比尚可。

### 书库/封面 "最近阅读"横滑区当前不可达(成品架并入书库后成孤儿功能)

**现状**: `renderShelf`(cover.js 第 57-83 行)只在 `kind !== 'original'` 时渲染(`library_view.js` 第 77 行
`isOriginal ? null : el('div','library-shelf')`); 但 main.js 第 40 行只创建一个 `original` 实例, 第 114 行
`products` 路由直接重定向回 `library`。所以"最近阅读"横滑区和 `library-shelf` 整段 CSS(第 147-184 行)在运行的
应用里从不出现。
**对比**: 苹果式"最近阅读"横滑封面本是很好的快速续读入口, 现在用户只能在主网格里靠"最近打开"排序找到上次的书。
**方案选项**:
  - 方案 A(把 shelf 挂回书库页顶部): 去掉 `isOriginal` 条件, 让书库也显示"最近阅读"。改动 ~3 行, 立即复活该功能。
  - 方案 B(接受现状, 删掉死代码): 既然默认排序就是 recent, 认为 shelf 冗余, 删 cover.js 的 renderShelf 和相关 CSS。
**建议权重**: 中(倾向方案 A)—— 改动极小, 但要不要和"最近打开排序"重复展示需拍板。

### 书库/封面 冷启动空态闪烁 + 搜索无清除按钮/无结果计数

**现状**: 首次进入书库, `store.state.books` 还是 `[]` 时(store.js 第 11 行初始值), render 第 166-170 行立即渲染

**对比**: 成熟产品冷启动显示骨架屏/加载态而不是"空"; 搜索框有清除按钮和结果计数。
**方案选项**:
  - 方案 A(区分"加载中/空/无结果"三态): render 前先标 loading, 数据回来前显示骨架或"加载中…", 而不是"空的"。改动 ~15 行。
  - 方案 B(搜索框加清除按钮 + 结果计数): ~8 行, 独立小项。
**建议权重**: 低(方案 A 影响每次冷启动观感但只有一瞬间; B 更小)。
