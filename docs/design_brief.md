## 我想要什么

这不是一次"给现有界面换皮"。我想要的是:**从"人在学一门外语时到底经历什么"
出发,重新想这个阅读器应该是什么样子**。

现有实现是工程驱动堆出来的,交互决定大多没有依据。我希望你在认知心理学、
学习科学和交互设计上认真发挥,提出有理有据的方案——哪怕它推翻现在的做法。
**我更看重"为什么这么设计"的论证,和大胆但站得住脚的想法,
而不是把已有功能重新排一遍。**

## 使用这个软件的人和处境

一个成年人,中文母语,英语中上水平,想通过"读整本英文原著"来真正提高。
他把一本书丢进软件,离线跑几十分钟,得到:原文 + 中文翻译 + 中文语法讲解 +
高质量朗读音频 + 逐词时间轴。然后他在这个阅读器里做两件事:

**场景 A — 自己精读(每天,长时间)**
一个人,晚上,连续读一两个小时。他要理解句子、遇到生词查一下、
把值得记的词收进生词本、听朗读跟读练口语。
他最怕的是:被界面打断心流;以及"偷看翻译"太容易导致其实什么都没学会。

**场景 B — 陪孩子读(周末,一起坐着)**
孩子自己念,大人在旁边看着,随时指出生词和读音。
孩子需要**跟得上朗读节奏**(所以逐词高亮对小孩的专注力引导帮助很大,
这是实际观察到的),但孩子也**极容易被界面元素吸引走注意力**。
大人需要能随时介入(暂停、重复这一句、指出某个词),但不该抢走孩子的主导感。

同一套软件、同一套设计语言,要同时服务这两个场景。

## 我希望你认真想的问题(命题核心)

不必按顺序,也不必全答,但我希望看到这个层次的思考:

- **"看答案"这件事怎么处理?** 现在的做法是译文和讲解默认高斯模糊、
  点一下才揭示——意图是制造"必要难度"(desirable difficulty),
  逼人先自己理解再核对。但模糊是最好的机制吗?揭示的成本应该多高?
  揭示之后该不该记住这个状态?一句已经揭示过的话,下次再读到应该什么样?
  从提取练习(retrieval practice)和测试效应的角度,还有别的做法吗?

- **原文、译文、讲解三者的空间关系应该是什么?**
  现在是上下三行绑在一起。这确实避免了视线长距离跳转(减少分散注意力效应),
  但也意味着译文永远在余光里。有没有更好的解法?
  成人和孩子需要的关系一样吗?

- **专家反转效应怎么体现?** 同一个人在不同章节、不同难度下需要的支撑不同。
  界面应该能感知并适应吗?还是应该完全交给用户手动控制?
  自动适应会不会让人失去掌控感?

- **逐词高亮到底在为谁服务、代价是什么?**
  对孩子它是节奏引导;对成年人,持续跳动的高亮会不会反而干扰阅读?
  什么时候该有、什么时候该消失?

- **多种视觉状态叠加时怎么办?** 同一个词身上可能同时是:
  正在被朗读 / 可点击查词 / 已在生词本里 / 属于一个短语动词。
  四种意义叠在一个词上,如何让人一眼分清而不是变成噪音?
  这里可能需要重新想"状态"该不该都用颜色表达。

- **控件密度与心流。** 现在顶部有十几个控件常驻。什么该常驻、什么该隐藏、
  什么该用手势或快捷键?怎么让"读"这件事占据绝对主导,
  又不至于让人找不到功能(Hick 定律与可发现性的平衡)?

- **跟读(shadowing)是个什么体验?** 重复某句 N 次、句末留白、变速、
  A-B 区间循环——这些参数怎么才能不像一堆工程旋钮?
  跟读时人的注意力在耳朵和嘴上,不在屏幕上,界面该怎么配合?

- **孩子的自主感。** 大人在旁边,但主导权应该在孩子手上。
  界面怎么支持"大人指导但不接管"?

欢迎引入我没想到的理论视角和设计模式。

## 现状(仅供参考,**全部可以推翻**)

以下是现在的做法和当初的意图。**不是要求保留**,是给一个起点,
以及告诉你哪些地方我已经知道有问题。有更好的方案请直接提,只要说明理由。

- 一句 = 一个"原子块",三行:原文 / 译文 / 讲解。
- 译文和讲解默认高斯模糊,点击单行揭示。
- 原文每个词是独立可点的 span,点击查词;短语动词多词联动高亮、整体查词。
- 已加入生词本的词有独立视觉态。
- 每个块左侧有独立播放三角(点正文不触发播放,降低误触)。
- 朗读时逐词卡拉OK式高亮推进;可切句级/词级两种粒度。
- 顶部三条横栏堆叠:导航栏 + 播放进度条 + 跟读参数条。
  **这块我明确不满意**:十几个圆形按钮挤一排,中文标签折成竖排,
  正文被压到很下面。看起来像功能原型不像成品。
- 跟读参数是一排裸的数字输入框(重复次数 / 留白毫秒 / 速度)。
  **这块我也明确不满意。**
- 章节可能几十章;原书插图会按原位插进正文流。

**不需要设计错误/失败状态**——产品上决定在处理阶段就把失败内容拦掉,
能进入阅读的书一定是完整的。

## 落地时必须成立的约束(只有这些是硬的)

这些不是设计偏好,是物理和平台限制:

1. **纯 HTML / CSS / 原生 JS**。没有 React/Vue/Tailwind。
   渲染层(Tauri + WebView2,基于 Chromium)就是生产代码,
   产出会直接进项目跑,所以不能是效果图。
2. **零外部资源**。严格 CSP:不能引 CDN、Google Fonts、外链图片。
   字体只能用系统字体栈。
3. **性能**:一章可能 3000+ 个词级 span,朗读高亮由 requestAnimationFrame
   以 60Hz 驱动。**逐帧变化的那部分样式**只能用合成友好的属性
   (transform / opacity / color / background-color),
   不能逐帧动 box-shadow / filter / 尺寸类属性。非逐帧的静态样式随便用。
4. **浅色 + 深色都要**。
5. **用 CSS 自定义属性表达设计决定**(颜色、圆角、字号、间距都走变量),
   项目有 lint 强制禁止裸 #hex。
   现有令牌是 Material Design 3 风格的一套(`--md-sys-color-*` 27 个 role、
   `--md-sys-radius-*`、`--md-sys-elevation-*`、`--md-sys-font-size-*`、
   `--md-sys-space-*`)。
   **可以新增令牌、改取值、也可以提议换一套体系**——
   只要最终是"令牌驱动"的,而不是散落的写死值。
6. 桌面窗口,默认 1100×800,最小 800×600。界面文字中文,正文英文。
7. 儿童场景的差异**倾向于**用同一套令牌的不同取值实现,而不是第二套 CSS
   (维护性考虑)。如果认为这个约束会严重损害设计,可以论证后突破。

## 期待的产出

**先发散,再收敛。**

第一步:提出 **2–3 个方向明显不同的设计概念**,每个说清楚:
核心主张是什么、基于什么心理学/交互原理、
在场景 A 和场景 B 分别表现如何、放弃了什么。
不要三个方案其实是同一个东西的三种配色。

选定方向后,再做可运行的 HTML/CSS 组件。
组件阶段用**真实规模的假数据**(至少几十句连续英文段落 + 中文译文 +
中文语法讲解),不要三五句的玩具数据——长文排版的问题只在真实长度下才暴露。

另外:请标出哪些设计决定是有风险的、需要实际用一段时间才能验证对不对。
诚实标出来比全都说得很确定更有价值。
