# aidulc 项目记忆 — 用户旅程审计 (2026-08-09)

按全局 CLAUDE.md 框架记录 UX 审计结论。以实测为准，发现现状与本文件矛盾时以现状为准并回来改本文件。
范围：完整用户操作面 13 个入口 × 四段旅程（前置/进行中/结束/再次进入）+ 逐条检查项（反馈即时性/状态可见性/错误与极端/默认预填/防呆保护/心智模型）。

## 最初以为 A 实测发现是 B（审计最有价值的记录）

1. **创建译本弹窗三节错位 (A1)**：最初以为 bug 是"控件被重复 `appendChild` 移动到了末尾"，修复=删掉异步里的重复挂载。**实测发现 profileSelect/langRow 从未在顶部挂载过，异步回调里的 append 是它们唯一的挂载点**——删掉后档案/语言控件直接不渲染，比原错位更糟。正确修法：三个控件都在初始阶段同步挂到各自标题之后，异步回调只负责往模型下拉填选项与告警。
   **通用教训：DOM 的 `appendChild` 对已是同父节点的子节点是"移动到最后"语义；删"冗余挂载"前先确认它不是唯一挂载点。** 该路径已有回归测试 `reader/tests/_smoke_views.mjs` 第 4 节。
2. **"取消"任务**：最初以为任务可取消。实测 `cancel_prep_job` 在 Rust 注册、`AiduJobService.cancel()` 定义，但**零前端调用**——只有"暂停"。任务行的"移除"原先也不杀子进程。
3. **移除排队任务**：最初以为正常移除。实测 `job_remove` 只删 DB 行、不清内存队列；`pump_queue` 弹出已删 id 后 `repo.get` 报"任务不存在"直接返回 → **后续排队任务全部停摆且无任何提示**（"后台失败但用户以为成功"的实例）。
4. **词典守护 vs 备料**：最初担心 `spawn_prep` 杀掉常驻词典守护后，读书记查词会静默失效。实测 `dict_daemon::lookup` 的 stale 判断会懒重建，面板显示"查词中…"+ 重试，冷启动 ~7s 有可见反馈，不静默。
5. **磁盘空间**：向导硬件检查最初硬编码 `C:\`；书库可迁移到别的盘，显示的可用空间与真实写入盘无关。改为从 `library_dir_get` 取实际 out_dir 所在盘。

## 状态管理（队列 / 生命周期）

- **启动自愈（杀进程/断电后重开）**：`main.rs` 启动时 `reset_stale()`（running→queued）+ 收集 queued 恢复队列注入内存队列 + `pump_queue` 自动续跑；书卡卡在 `processing` 的恢复为 `pending`（书库可见可重试）；`cleanup_orphans` 清孤儿 edition。不会出现永远"处理中"的僵尸任务。
- **`job_remove` 现在（2026-08-09 修）**：运行中先 `child.kill()`（否则侧车继续烧 GPU、写孤儿产物），并从内存队列清除 id，再删 DB 行。`pump_queue` 对缺失 id 改为跳过继续，不再整条队列停摆。
- **移除任务确认**：`prep_view` 移除按钮按三态弹确认——运行中"立即停止处理并丢弃当前进度"、排队中"不会再进入处理"、已完成"仅移除记录"。
- **暂停/继续**：暂停=kill 子进程留 checkpoint，继续=重新入队续跑。checkpoint 契约由侧车 `prep/tests/test_g2_checkpoint.py` 锁定（失败阶段可重试、`reconcile_position_checkpoint` 位置对齐、原子写、损坏容忍）。GUI 层暂停→继续按钮交互仍需真人点一遍最终确认。

## 错误处理与反馈

- **任务完成通知**：前端全局监听 `job-progress` 的 `job_done`，等 300ms 让收尾线程落盘状态后 toast「《x》处理完成，可以开始阅读了」/ 失败则「处理失败，去阅读准备查看原因」。长任务不再需要用户自己回来刷新才知道结果。
- **实时进度人话**：`prep_view` 实时事件里的 stage 是英文（translate/nlp），已统一走中文映射（翻译/分词）；补 `queued/retry_failed` 标签。
- **进度条与百分比标签一致**：后端 `enrich_progress` 的 stage_progress/stage_done 事件新增 `progress` 字段（全书完成度，复用 `overall_progress`）；前端 `_updateTask` 用它同时刷进度条和 `prep-pct` 标签。此前条按阶段比例、标签按全书进度，两套数字实时打架。Rust 单测 `enrich_progress_carries_overall_progress` + `_smoke_views` 第 1b 节锁定。
- **去模型中心直达**：`#/models` 重定向设置页时带一次性 `settingsTab` 意图，直接激活「模型中心」tab（此前落在默认"系统与书库"页）。用后清除，下次进设置回默认。
- 查词失败有"重试"；词典守护失败明确说"模型已配置但未返回结果"，不误导成未配置。
- **阅读器设置持久化不再静默失败**：`_persistSettings` 曾是无 catch 的 fire-and-forget，改字号/主题后若写入失败，下次打开被静默还原（"后台失败但用户以为成功"）。已加 `.catch` → `_setStatus('设置保存失败 (磁盘写入失败?)')`，与 `_saveProgress` 同一反馈通道。设置页三处 upsert 原本就有 toast，唯独阅读器这条漏了。

## 本次不做（显式列出，防日后悄悄消失；每项有理由）

- **用户可见的「取消」按钮**：完整取消需后端 canceled 状态机与暂停/重试联动，风险大于收益；"移除+三态确认"已覆盖放弃任务的核心诉求。
- **耗时预估 / ETA**：需要侧车历史任务耗时统计，是一条新数据管道。
- **磁盘满预检**：需统一磁盘策略与任务体积预估，影响面大；当前写失败会走 job failed 可见。
- **下载切页状态恢复**：需全局下载中心，是重构不是修补。
- **阅读设置 undo/重设为默认**：交互模型新增，收益有限。
- **任务完成桌面通知**：需 OS 通知渠道，先有前台 toast。
- **大 zip 导出/导入异步化**：当前同步阻塞仅在几十 MB 级出现。
- **生词批量管理**：增量功能，不属手感打磨。
- **部分失败书内失败句标记**（阅读器内标出缺译文/缺音频的句子）：需要读 quality_report 进阅读器，中成本，未做。
- **查词 vs 处理中并发占用 GPU（反向场景）**：`spawn_prep` 会先杀词典守护释放显存（F21），但若处理任务进行中用户回阅读器**查词**，`dict_daemon::lookup` 会重新拉起第二份 LLM 驻留显存，小显存卡上可能压垮处理任务（失败可见，不静默）。未加"处理中禁止查词"的守卫：需跨模块传递"prep 运行中"标志，且无法在本环境实测显存行为；作为已知风险显式记录，处理前先实测确认。
