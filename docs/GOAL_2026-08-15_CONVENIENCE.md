# 便利性/完整度需求挖掘(2026-08-15)

## 这份文档是什么

跟 2026-08-14 的"成熟度审计"(见 `ROADMAP.md`"成熟度审计"节)是两种不同性质的挖掘:

- 2026-08-14 那轮找的是**正确性/边界缺口**——按 CLAUDE.md 的五个维度(配置管理/
  外部系统集成/依赖交付/状态管理/错误反馈)逐域核对, 找"会出错但没处理"的地方。
- 这一轮找的是**便利性/完整度缺口**——不是"错了", 是"一个成熟产品这里通常会有,
  但这里没有"。起因: 用户实测书库页发现排序/卡片大小/生词发音都是这类"顺手的
  需求", 用户原话"这种需求我还是觉得应该是成熟度带出来的, 而不是我需要想到的"。

用 progate(deepseek-v4-pro)逐域深挖, 编排方(当前会话)只做范围框定和轻量复核,
**这一轮不改代码**, 只产出带方案选项和取舍权重的报告, 由用户最后拍板选哪些做。


### 书库/封面 搜索只匹配书名、不匹配作者

**现状**: `library_view.js` 第 197 行 `(b.title || b.id).toLowerCase().includes(q)` —— 搜索框只对书名/id 做
子串匹配。书名/作者已经在卡片上拆成两行显示(第 223-228 行, `AiduTitleCleanup.parseBookTitle` 拆出 `author`),
但作者值不进搜索索引。排序下拉 `_sortBooks`(第 405-431 行)也只有 recent/title/progress/added 四轴, 没有"作者"轴。
**对比**: 微信读书/Kindle/Calibre 都支持按作者搜到该作者全部书; "记得是村上春树那本、想不起书名"是极常见场景。
**方案选项**:
  - 方案 A(搜索补作者): 第 197 行把匹配范围从 `b.title` 扩到解析出的 `author`(需在 `_renderBooks` 里缓存解析结果)。改动 ~5 行, 立即见效。
  - 方案 B(再加作者排序): 排序下拉加"作者 A-Z"。改动也小, 但作者值来自文件名清洗, 可能不干净。
**建议权重**: 高(方案 A)—— 高频 + 改动极小。

**对比**: 成熟产品里"部分失败"卡片的失败计数通常是可点/带"重试"动作的, 或至少一键跳到失败详情。

### 书库/封面 没有批量操作(多选删除/导出)

**现状**: 删除只在 `_openBookMenu` 里单本触发(第 527-539 行), 每本要"点 ⋯ → 点删除 → 点确认"三步; 导出同样

**方案选项**:

**建议权重**: 中高(方案 A)—— 高频且是"成熟度"硬指标, 但需后端支持批量删除(目前 `remove` 是单 id, library_service.js 第 23 行)。
