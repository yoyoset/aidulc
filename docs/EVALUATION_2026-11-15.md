# aidulc 项目评估与改进方案(2026-11-15)

> 评估方: Claude。范围: 全仓库(Rust 壳 / Python 侧车 / reader 前端 / cloud 同步端)。
> 本文分两个角度(技术、用户)给出问题与方案, 最后合并成一份分阶段的执行计划。
> 每条结论都标了依据; 没有实测的地方在第 2 节和第 8 节明确写出。

## 1. 结论

工程纪律很强, 功能面已经超出个人工具的需要。现在的短板不在代码质量, 而在三处:

1. **数据安全没有闭环**: 能建快照、不能恢复; 代码本身 12 个提交只在本机。
2. **交付不可复现**: 侧车依赖没有声明, 没有版本和发布流程。
3. **用户侧的"坏消息"传不到用户**: 同步合并失败仍显示成功、部分失败的句子在阅读器里看不出来、
   长任务完成没有系统通知。

建议接下来停止加新功能, 按第 6 节的三个阶段做一轮"稳固 → 可交付 → 开箱体验"。

## 2. 评估方法

| 方式 | 内容 |
|---|---|

推断而非实测的条目单独标了"判断"。

## 4. 技术角度

### 4.1 做得好的(保持)

- 门禁真在跑, 且覆盖了容易漂移的东西: 契约拷贝一致性、命令注册与前端 invoke 的名称和参数、
  裸色值、对比度、函数长度基线。
- 存储单一写者规则和 `contracts/` 单一来源执行得住, 两处例外都写明了理由并有测试锁定。
- 侧车有 checkpoint 契约和失败阶段重试契约, 长任务可中断可续跑。
- 记忆文档记录"最初以为 A, 实测是 B", 对排查同类问题有实际价值。
- 版权边界(服务端不接收书文件)在架构上守住了。

### 4.2 问题与方案

**T1 代码没有异地副本(P0)**
- 依据: `git status -sb` 显示 `main...origin/main [ahead 12]`, 包含全部丢库防护提交。
- 方案: 提交在途改动(契约 + 新测试一个提交, 文档一个提交), 然后推送。
- 验收: `git status -sb` 不再显示 ahead; 工作区只剩 `.claude/`、`.mcp.json`、`.gitignore` 这三类
  与本项目无关的改动。

**T2 快照只能建, 不能恢复(P0)**
- 依据: `infrastructure/snapshot.rs` 每天 `VACUUM INTO` 到 `%APPDATA%\aidulc\snapshots\`;
  `commands/`、`ipc/registry.rs`、`reader/views/` 里没有任何读取或恢复快照的代码。
- 方案: 新增 `snapshot_list` / `snapshot_restore` 两个命令。恢复前先把当前 `data.db` 另存一份
  (`data-before-restore-<时间>.db`), 再替换并要求重启。入口放两处: 设置页"系统与书库", 以及
  "找不到书库"弹窗(见 U2)。
- 验收: Rust 单测 `snapshot_restore_roundtrip`(写入数据 → 快照 → 改数据 → 恢复 → 读回原值)和
  `snapshot_restore_keeps_pre_restore_copy`。
- 不做: 不备份书包和音频(体积大, 可重跑生成)。在恢复界面写明"只恢复生词、进度、摘录、设置"。

**T3 侧车运行环境不可复现(P1)**
- 依据: `prep/pyproject.toml` 没有 `dependencies`, 文件头注释却写"直接依赖固定精确版本 + 锁文件
  策略"; `prep/setup.ps1` 只装 pytest; 仓库里没有任何 requirements 或 lock 文件。代码实际 import
  `torch`、`kokoro`、`llama_cpp`、`spacy`、`numpy`、`soundfile`、`fitz`。本机 venv 里是
  torch 2.6.0+cu124、kokoro 0.7.16、spacy 3.8.14、numpy 2.5.1、soundfile 0.14.0、pymupdf 1.28.2。
- 影响: 换机器或 venv 损坏后, 无法装回同一套版本; PyInstaller 打出的侧车取决于当时碰巧装了什么。
- 方案: 把直接依赖按当前 venv 的版本写进 `pyproject.toml`(torch 的 CUDA 轮子源单独注明);
  `pip freeze` 生成 `prep/requirements.lock` 入库; `setup.ps1` 改成按锁文件安装; `check.ps1` 加一项
  "venv 与锁文件一致"。
- 验收: 在一个全新目录按 `setup.ps1` 建 venv 后 `pytest prep\tests` 全过; 门禁新增项 PASS。

**T4 锁中毒会连锁崩溃(P1)**
- 依据: `src-tauri/src` 里 224 处 `lock().unwrap()`, 0 处中毒恢复; 数据库是单个
  `Mutex<Connection>`(`store_mod.rs:23`)。任一线程持锁时 panic, 之后每个命令都会在取锁处 panic,
  用户看到的是整个应用所有操作都失败, 只能重启。
- 方案: 在 `Db` 上加一个取连接的方法, 内部用 `unwrap_or_else(|e| e.into_inner())` 恢复; 队列、子进程
  等其它锁同样处理。SQLite 连接在 panic 后仍然可用(事务会回滚), 所以恢复是安全的。机械替换,
  适合委派。
- 验收: 单测 `db_lock_survives_panicked_holder`(一个线程持锁 panic 后, 主线程仍能查询);
  `grep -c "conn.lock().unwrap()"` 在非测试代码里为 0。

**T5 同步合并失败被当成成功(P1)**
- 依据: `application/sync_service.rs:409` `let _ = merge_remote_into_local(...)`; 紧接着第 412 行
  起把 `last_pull_rev` 推进到 `pr.rev` 并 `record_sync(..., Ok(()))`。合并一旦失败, 这批远端变更
  不会再被拉取, 界面显示"已同步"。
- 方案: 合并失败时不推进 `last_pull_rev`, 把错误记进同步状态并在设置页显示。同时把非测试代码里的
  `let _ =`(全库 370 处, 含测试)过一遍, 分成"确实可忽略"和"必须上报"两类, 前者加一句理由注释。
  `store_mod.rs:41` 的 `pragma_update(foreign_keys).ok()` 也在这批里。
- 验收: 单测 `pull_merge_failure_does_not_advance_rev`; 审查清单附在提交说明里(每个文件处理了几处)。

**T6 配对码限流防不住枚举(P2, 卖托管前升 P1)**
- 依据: `cloud/worker/src/index.js:199` 和 `recordFail`(244 行)把失败次数记在
  `'codefail:' + code` 上, 键是**被猜的那个码**。攻击者每次换一个码, 永远触发不了 5 次上限。
  码空间 100 万, 有效期 10 分钟。
- 修正记录: 2026-11-14 的口头报告里我写的是"未见限流", 依据是 grep 没搜到 rate/attempt 字样。
  读代码后发现限流存在, 但键选错了。以这一条为准。
- 方案: 改成按来源(CF 用 `CF-Connecting-IP`, VPS 用连接地址)计失败次数; 再加一个全局上限
  (存在未用的码时, 全站每分钟兑换失败超过 N 次就暂停兑换)。
- 验收: `cloud/worker/test/local_test.mjs` 新增"同一来源用 6 个不同的错误码, 第 6 次返回 429"。

**T7 没有版本和发布流程(P2)**
- 依据: `tauri.conf.json` 和 `Cargo.toml` 版本一直是 0.1.0; 唯一的 tag 是 8 月的
  `v0.1.0-working-3books`; `CHANGELOG.md` 全部堆在 `[Unreleased]`; 没有 CI; `dist/aidulc-portable`
  里 exe 是 11-10 的, `config.toml` 是 8-08 的。
- 方案: 写一个 `scripts/release.ps1`: 跑门禁 → 改三处版本号 → 切 CHANGELOG → 重建侧车 → 组装便携包
  → 打 tag。先打 `v0.2.0`。CI 暂不做(单人项目, 本地门禁已经够; 等有第二个贡献者再说)。
- 验收: `git tag` 有 `v0.2.0`; 便携包里的 exe 版本号与 tag 一致。

**T8 文档失去收敛(P2)**
- 依据: `docs/` + `memory/` 约 1.3 万行; `ROADMAP.md` 1042 行, 自己写着"漂移记录"; 成熟度审计
  37 条里 31 条已标完成却仍留在文件里(违反它自己"完成就删"的规则); 根目录有 `08-10plan.md`、
  `TASKS.md`(8-17, 条目均已完成)、`aidu-subgen-comicgen-cf-lazy-gosling.md`、两个设计 zip。
- 方案: 已完成的 GOAL / STAGE_REPORT / WATCH 移进 `docs/archive/`; ROADMAP 只留开放项, 目标 200 行
  以内; 根目录过期文件归档或删除; 本文第 6 节的任务并入 ROADMAP 后, 本文也归档。
- 验收: `wc -l docs/ROADMAP.md` 小于 200; `docs/` 顶层文件数不超过 12。

**T9 超长函数没有下降(P3)**
- 依据: 17 个超过 150 行, 等于基线。`migrate` 1201 行、`main` 427 行、`system_tab.js::render`
  430 行、`atomic_block.js::create` 338 行、`pump_queue` 308 行。
- 方案: 只拆两个收益最高的: `system_tab.js::render`(按设置分组拆)和 `main`(启动装配拆成
  解析数据根 / 开库 / 恢复队列 / 构建 Tauri 四段)。`migrate` 不拆, 顺序本身是文档。
- 验收: `functionOverBaseline` 从 17 降到 15。

**T10 其它(P3, 顺手处理)**
- `dictionary_panel.js:88`、`:179` 把单词直接拼进 `innerHTML`; `review_view.js:72`、
  `vocab_view.js:157` 把错误文本直接拼进去。CSP 挡住了内联脚本, 实际风险低, 改成 `textContent` 即可。
- Rust 测试必须 `--test-threads=1`(共享临时库)。可以改成每个测试用独立临时目录, 但收益只是测试
  快一些, 排在最后。

## 5. 用户角度

按用户走过的路径分段。每段先写现状, 再写问题和方案。

### 5.1 首次上手

**U1 开箱看不到核心卖点(P1)**
- 现状: 内置样书存在(`commands/library.rs:9`), 但它是"无音频的轻量文本样书", 原创短句。
  跟读、逐词高亮、时间轴这些最有辨识度的功能, 新用户要先装约 6GB 模型、有 12GB 显存的 N 卡、
  再跑完一本书才能看到。
- 修正记录: 11-14 口头报告里我说"下一个有价值的功能是内置公版样书"。实测发现文本样书 8 月已做,
  缺的是**带音频的成品包**。以这一条为准。
- 方案: 用现有管线跑一篇 CC0 短篇(ROADMAP"内置公版样书"一节已有选书要求), 产出带音频的成品包。
  体积先实测, 再决定随便携包带还是首次运行时下载。向导完成页改成"先读这本; 想处理自己的书时再
  装模型"。
- 验收: 全新数据目录、未登记任何模型的情况下, 走完向导能打开样书并播放出声(冒烟 + 一次人工确认)。

**U2 出事时用户无法自救(P0, 与 T2 同一件事的用户面)**
- 现状: "找不到书库"弹窗有三个按钮(重新指定 / 原位置新建空库 / 改用默认位置), 没有"恢复数据"。
  用户真遇到 11 月那种情况, 仍然只能面对一个空库。
- 方案: 弹窗加第四个选项"从最近的快照恢复(日期, 生词数)", 文案写清恢复什么、不恢复什么。
- 验收: 冒烟检查"存在快照时弹窗出现该按钮, 且显示快照日期"。

### 5.2 导入与备料

**U3 长任务完成只有前台提示(P2)**
- 现状: 备料以小时计; 完成时只有应用内 toast。全库没有系统通知相关代码。剩余时间估计已经有了
  (`prep_view.js:392`)。
- 方案: 接 `tauri-plugin-notification`, 任务完成或失败时发系统通知; 设置里给一个开关。
- 验收: 冒烟检查"job_done 事件触发通知调用"; 人工确认窗口最小化时能看到。

**U4 磁盘不够要跑到写失败才知道(P2)**
- 现状: 没有任何可用空间预检代码。
- 方案: 开始备料前按句数估算体积(参照已记录的 8007 句约 24MB), 不够时阻止并说明差多少。
- 验收: 单测覆盖估算函数; 冒烟检查空间不足时出现阻止文案。

### 5.3 阅读

**U5 部分失败的句子在阅读器里看不出来(P1)**
- 现状: 任务状态可以是"部分完成", 但 `reader_view.js` 和 `components/` 里没有任何读取
  `failedStages` 或质量报告的代码。用户读到某句没有译文或没有声音, 无法分辨是程序坏了还是这句
  本来就失败了, 也没有就地补救的入口。这条 8 月的 UX 审计已列为"本次不做"。
- 方案: 失败句在正文里加一个低调的标记(沿用现有语义色令牌), 点开显示"缺译文 / 缺音频"和
  "重试失败句"按钮(后端命令已有)。书卡上显示失败句数。
- 验收: DOM 冒烟"带 failedStages 的句子渲染出标记, 正常句不渲染"。

**U6 可访问性基本空白(P3)**
- 现状: 视图和组件里 `aria-label` 只有 4 处; 样式里没有 `prefers-reduced-motion`。
- 方案: 给只有图标的按钮补 `aria-label`; 平滑滚动和过渡动画尊重系统的减少动态设置。
- 验收: 冒烟检查"顶栏和阅读器工具条的按钮都有可读名称"。

### 5.4 生词与同步

**U7 同步显示成功但进度没回来(P1, 即 T5)**
- 用户看到的: 手机上复习过的词, 桌面端状态没变, 而设置页写着"已同步"。
- 方案见 T5。用户面补一句: 同步状态行出现错误时, 给"重新拉取"按钮。

### 5.5 更新与维护

**U8 用户不知道有新版本(P2)**
- 现状: 没有版本检查; 设置页是否显示当前版本号没有核实。便携版更新靠手动替换文件。
- 方案: 设置页显示版本号和"检查更新"(只查 GitHub release 的版本号并给下载链接, 不做自动更新和
  签名——那是有付费用户之后的事)。
- 验收: 冒烟检查设置页出现版本号; 单测覆盖版本比较函数。

### 5.6 整体(判断, 非实测)

**U9 概念负担偏重, 且基础入口仍在出问题**
- 依据: 用户要理解原书 / 译本 / 学习档案 / 备料 / 模型中心 / 全局推荐 / 兜底这一串概念。11 月最近
  两个提交是"空书库不渲染导入卡, 用户找不到任何导入入口"和"模型页把当前全局推荐 / 实际兜底讲
  清楚"——上线三个月后仍在修"找不到入口""看不懂状态"这一级的问题, 说明没有一条固定的新用户
  走查。
- 方案: 写一份 `docs/SMOKE_NEW_USER.md`: 全新数据目录下的 10 步人工走查(向导 → 读样书 → 导入一本
  → 创建译本 → 阅读 → 查词 → 加生词 → 复习 → 备份 → 模拟丢库恢复), 每次发版前走一遍, 发现的问题
  记回 ROADMAP。这比再做一轮 UX 审计便宜, 而且可重复。
- 验收: 文档存在; `release.ps1` 在打 tag 前提示确认已走查。

## 7. 这一轮不做

| 事项 | 理由 |
|---|---|
| clippy 基线清零(多参数函数改请求结构体) | 要同时改命令调用约定和前端传参, 改动面大, 不解决上面任何一项 |
| 字号 / 间距令牌存量迁移 | 几百处, 每处要核对视觉, 没有用户可感知的收益 |
| 阅读器虚拟滚动 | 没有实测证明分帧渲染不够用 |
| 自动更新、代码签名、CI | 单人项目且没有付费用户; 本地门禁目前够用 |
| 书包和音频的备份 | 体积大且可重新生成; 快照只保不可再生的数据 |
| 拆 `migrate` | 顺序迁移链本身是文档 |
| 新功能和新一轮 UX 打磨 | 先把已有功能的失败路径补齐 |

## 8. 评估的局限

- 没有运行应用。U9 是判断; U3、U4、U6、U8 的"现状"来自 grep 零命中, 存在换了名字没搜到的可能,
  动手前先各自确认一次。
- `let _ =` 的 370 处只读了 `sync_service.rs` 那一段, 其余是否有问题要等 S5 的审查。
- 没有评估翻译和讲解的内容质量, 也没有评估 TTS 对齐精度, 这些需要真实书籍和人耳。
- 工期是粗估, 没有历史数据支撑。
