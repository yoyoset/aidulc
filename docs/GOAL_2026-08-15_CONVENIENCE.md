# 便利性/完整度需求挖掘(2026-08-15)

## 这份文档是什么

跟 2026-08-14 的"成熟度审计"(见 `ROADMAP.md`"成熟度审计"节)是两种不同性质的挖掘:

- 2026-08-14 那轮找的是**正确性/边界缺口**——按 CLAUDE.md 的五个维度(配置管理/
  外部系统集成/依赖交付/状态管理/错误反馈)逐域核对, 找"会出错但没处理"的地方。
- 这一轮找的是**便利性/完整度缺口**——不是"错了", 是"一个成熟产品这里通常会有,
  但这里没有"。起因: 用户实测书库页发现排序/卡片大小/生词发音都是这类"顺手的
  需求", 用户原话"这种需求我还是觉得应该是成熟度带出来的, 而不是我需要想到的"。

用 progate(deepseek-v4-pro)逐域深挖, 编排方(当前会话)只做范围框定和轻量复核,
**这一轮不改代码**, 只产出带方案选项和取舍权重的报告, 由用户最后拍板选哪些做。

### 书库/封面 搜索只匹配书名、不匹配作者

**现状**: `library_view.js` 第 197 行 `(b.title || b.id).toLowerCase().includes(q)` —— 搜索框只对书名/id 做
子串匹配。书名/作者已经在卡片上拆成两行显示(第 223-228 行, `AiduTitleCleanup.parseBookTitle` 拆出 `author`),
但作者值不进搜索索引。排序下拉 `_sortBooks`(第 405-431 行)也只有 recent/title/progress/added 四轴, 没有"作者"轴。
**对比**: 微信读书/Kindle/Calibre 都支持按作者搜到该作者全部书; "记得是村上春树那本、想不起书名"是极常见场景。
**方案选项**:
  - 方案 A(搜索补作者): 第 197 行把匹配范围从 `b.title` 扩到解析出的 `author`(需在 `_renderBooks` 里缓存解析结果)。改动 ~5 行, 立即见效。
  - 方案 B(再加作者排序): 排序下拉加"作者 A-Z"。改动也小, 但作者值来自文件名清洗, 可能不干净。
**建议权重**: 高(方案 A)—— 高频 + 改动极小。

**对比**: 成熟产品里"部分失败"卡片的失败计数通常是可点/带"重试"动作的, 或至少一键跳到失败详情。
**方案选项**:

### 书库/封面 没有批量操作(多选删除/导出)

**现状**: 删除只在 `_openBookMenu` 里单本触发(第 527-539 行), 每本要"点 ⋯ → 点删除 → 点确认"三步; 导出同样

**对比**: 任何书库产品, 用户攒了几十本后要清理/迁移, 都会期望"勾选多本 → 一次删除/导出"。10 本时逐本操作已明显烦人。
**方案选项**:
  - 方案 A(卡片复选框 + 工具条批量删除/导出): 增加 `_selection` Set + 复选框/长按切换选择模式 + 工具条出现"删除 N 本"。改动中等(~40-60 行 + 样式), 覆盖面最大。

**建议权重**: 中高(方案 A)—— 高频且是"成熟度"硬指标, 但需后端支持批量删除(目前 `remove` 是单 id, library_service.js 第 23 行)。

### 书库/封面 删除没有撤销/回收站

### 同步 上次同步时间/失败原因只存内存, 重启即丢 → 顶栏云图标与设置页误报"离线"

**现状**: `sync_service.rs` 第 140-141 行 `LAST_SYNC` 是 `static OnceLock<Mutex<HashMap>>` 的进程内内存表,
`record_sync`(第 173-179 行)只在同步后往里写、`last_sync_for`(第 143-147 行)从这里读, **全仓没有任何地方从
`sync_state` 表回填这份内存**。而 `get_status`(第 195 行)把 `last_sync_for` 的结果喂给 `status_for`, 其中
`(true, None)` 分支(第 115-118 行)把"已配置但本进程内还没同步过"判成 `status: "offline"`。于是每次冷启动后:
① 顶栏云图标 `shell_view.js` 第 233-237 行按 status 显示 `cloud_off`"离线"(尽管实际已配置且上次同步成功);
② 设置页 `sync_tab.js` 第 148 行 `last_sync_at` 为 None → 不显示"上次"时间; ③ 第 161-163 行 `last_error` 同样
为 None → 上次失败原因也丢。讽刺的是 `sync_state.updated_at` 其实是持久化的(`sync_service.rs` 第 411-418 行
每次 upsert 都写 `updated_at: now`), 即"上次成功时间"已经落库, 只是从没被读出来显示。
**对比**: 任何同步产品(Google Drive/Dropbox/微信收藏)重启后仍显示"上次同步于 X 时间", 失败原因也保留;
"离线"和"已同步但本次会话没同步过"是两回事, 不该混成一个标签。
**方案选项**:
  - 方案 A(把 last_sync_at/last_error 落库并从 `sync_state` 读回): 给 `SyncState` 加 `last_sync_at`/`last_error`
    两列(迁移), `record_sync` 写库, `get_status` 里 last 从库读; `(true, None)` 分支按 pending_count 判
    synced/pending 而不是一律 offline。改动 ~20 行 + 一条迁移, 一次性根治误报。
  - 方案 B(只改状态判定, 不改落库): `(true, None)` 改为按 `pending_count == 0 ? synced : pending`, 消除"离线"
    误报, 但 `last_sync_at`/`last_error` 仍丢, 时间与失败原因还是不可见。改动 ~5 行, 治标。
**建议权重**: 高(方案 A)—— 顶栏图标是每次开机就看到的、常驻的, 误报"离线"会持续动摇用户对同步的信任;
且数据其实已经在库里, 只是没读出来。

### 同步 无"已配对设备"列表, 历史设备无法查看/远程踢除

**现状**: 踢设备的唯一入口是扫码配对弹窗里的"踢掉这台设备"(`sync_tab.js` 第 291-305 行), 它依赖刚生成的

**没有任何"列出该 user 全部设备 token"的端点或命令**。配对了一年的手机丢了/换新, 用户既看不到有几台设备连着,
也没有入口收回丢的那台——除非重新配对再踢掉新 token(而丢的那台 token 仍有效, "拿到链接的人能读你词库"的风险

标配安全项。
**方案选项**:
  - 方案 A(worker 加 /v1/auth/devices 列表端点 + 客户端命令 + 前端设备列表): 带 caller token 返回该 user 设备
    清单, 前端列设备并逐个可踢。改动大(动 worker + 契约 + 客户端 + UI), 但根治。
  - 方案 B(前端把配对过的 device_id/token 落本地记录, 之后还能踢同一台): 不改 worker, 但换设备/清数据后记录
    丢失, 且仍看不到"所有设备"全貌。
**建议权重**: 中(方案 A 记 ROADMAP 优先, B 是权宜)—— 安全/资产管理缺口, 但跨 worker 改动, 不宜顺手做。

### 同步 全量重推上千词时"立即同步"无进度反馈, 只有"同步中…"一次性出结果

**现状**: `syncBtn.onclick`(`sync_tab.js` 第 198-205 行)设一句"同步中…"后 `await AiduSyncService.now()` 一次性

**方案选项**:
  - 方案 A(`sync_endpoint` 分阶段发事件/返回进度, 前端显示阶段文案): 推/拉/合并三阶段各上报一次, 前端轮询或
    接事件。改动中等(需事件通道或分步命令)。
  - 方案 B(把"同步中…"换成按后端逐个更新文案): 前端按 `sync_now_all` 的数组边返回边显示"正在同步后端 1/2…",
    仍需后端支持流式; 或简单点把整句改成"推送中…(可能较久, 请勿关窗)"。改动小, 只安抚不解决。
**建议权重**: 低中(方案 A)—— 只在首配/换库全量重推时发生, 频率低, 但发生时的观感是"是不是卡死了"。

### 同步 "上次同步时间"只显示时分秒不显示日期, 隔天就误导

**现状**: `sync_tab.js` 第 148 行 `new Date(d.last_sync_at).toLocaleTimeString()` 只输出时分秒(如 "14:03:25"),

**方案选项**:

**建议权重**: 低(方案 A)—— 改动极小, 但和第 1 条"持久化"叠加后才真正有意义(重启后时间丢了, 显示格式也白搭)。

### 模型中心 下载进度只有百分比和 MB, 没有速度/剩余时间

**现状**: `models_view.js` 第 511-526 行 `_pollDownload` 每 1 秒轮询一次, 只算 `pct` 和 `readMB/totalMB` 两个数,
按钮文案是 `下载中… ${pct}% (${readMB}/${totalMB} MB)`。后端 `models.rs` 第 337-341 行 `models_download_status`
只返回 `bytes_read`/`total` 两个值, 没有时间戳也没有速率。Qwen3-4B 是 2.5GB(第 22 行 `sizeBytes: 2497280256`),
在慢网速下要下几十分钟——用户只能看到"已下了多少 MB / 百分之几", 不知道网速是多少、还要等多久。
前端明明 1 秒轮询一次(第 520 行), 相邻两次 `bytes_read` 差分即可算出实时速率和剩余时间, 但没算。
**对比**: 浏览器下载/Steam/HF 自带下载器都显示"X MB/s · 剩余 Y 分钟"; 几 GB 的大文件下载, 速度与 ETA 是
"要不要去倒杯水、还是去睡一觉"的决策依据, 只看百分比没有时间感。
**方案选项**:
  - 方案 A(前端差分算速率 + ETA): `_pollDownload` 里记上次 `bytes_read` 和时间戳, 相邻两次差分算 MB/s,
    按钮文案加 ` · ${speed} MB/s · 约剩 ${eta}`。纯前端 ~10 行, 零后端改动, 数据已全部在手。
  - 方案 B(后端在 `models_download_status` 里带速率/ETA): 下载线程在进度回调里记墙钟时间算速率透出。改动更
    "正规"但要在 DownloadJob 里加字段, 且前端已有 1 秒轮询, 后端算意义不大。
**建议权重**: 高(方案 A)—— 大文件下载的高频观感项, 纯前端改动极小。

### 模型中心 下载开始后无法取消, 点错只能等它下完或关应用

**现状**: `models.rs` 第 322-342 行的 `downloads_registry`(静态 HashMap)只有 `insert`/`retain`/`get` 三种操作,
没有任何"移除/取消"入口; 命令层也只暴露 `models_download`(第 225 行)和 `models_download_status`(第 332 行),
全仓没有 `models_download_cancel`。前端 `models_view.js` 所有下载按钮(`_doDownloadModel` 第 492 行、
`_downloadOne` 第 574 行)点下去后就是后台线程一路跑到完成, UI 上没有任何"取消"按钮。2.5GB 的模型点错家族
或点错目录, 要么眼睁睁等它下完, 要么直接关掉整个应用(而且 .part 断点会留着, 下次还会接着下)。
**对比**: 任何下载器(浏览器/Steam/应用商店)都提供"取消下载"; 大文件点错是常态, 取消是基本安全阀。
**方案选项**:
  - 方案 A(加 `models_download_cancel` 命令 + 按钮): 下载线程用 `AtomicBool` 取消标志, Read 循环每轮检查、
    置位后中断并删 .part; 前端按钮在下载中显示"取消", 点击调命令。改动中等(~40 行 + 前端 ~10 行),
    但下载器当前是 `reqwest::blocking` 同步读, 取消标志要传进 `download_with_progress`, 需小改签名。
  - 方案 B(只在前端加"放弃"按钮, 后端不停): 前端停止轮询、恢复按钮, 后台线程照跑到底但结果被忽略。
    改动小(~5 行), 但磁盘/带宽仍在被占, 是假取消, 治标。
**建议权重**: 中高(方案 A)—— 点错大文件下载是真实场景, 但改动要碰下载器签名, 可排期做。

    但频率低, 可后置。
**建议权重**: 高(方案 A)—— 数据已算好、纯接线, 且直接补上"删模型"这个高危动作缺失的前置可见性。

### 模型中心 模型目录/扫描路径不持久化, 重启后重新添加

**现状**: 页面顶部"模型目录"列表和扫描弹窗的扫描路径共用的 `this._modelDirs`(`models_view.js` 第 119 行赋值、

这条目录就消失了, 又得重新选一次。对"模型分散在多个盘/多个目录"的重度用户, 这是每次开机都要重复的劳动。
**对比**: 任何带"扫描目录/媒体库"的产品(音乐播放器、下载工具)都会持久化用户加过的目录; 目录是低频但

**方案选项**:
  - 方案 A(新增配置项持久化额外模型目录): 后端加一个 `runtime_config` 可写的 `extra_model_dirs`(存
    reader_settings 或单独配置), 前端"+ 添加目录"写回、`_loadModelDirs` 从配置合并读。改动中等(~30 行 +
    一个 set 命令 + 可能的存储表), 一劳永逸。
  - 方案 B(前端 localStorage 存目录列表): 不动后端, `_loadModelDirs` 里合并 localStorage 里存的自定义目录。
    改动 ~10 行, 但目录偏好是设备相关的配置, 放 localStorage 与项目里"学习档案用 localStorage"的先例一致,
    只是不同设备不共享。
**建议权重**: 中(方案 B 可先行, A 更正规)—— 多目录用户才遇到, 但发生就是每次重启都烦; B 改动小。

### 模型中心 已登记模型不提示"有新版", 更新只能靠重新扫描

**现状**: "有新版"判定 `_versionStatus`(`models_view.js` 第 315-331 行)只在**扫描候选列表**里调用(第 948 行),

**方案选项**:

  - 方案 B(进一步做"更新后提示删旧版"): 下载并登记新版后, 若同 family 有旧版且已解绑, 提示一并移除。改动

**建议权重**: 中(方案 A)—— 升级是重度用户高频动作, 但需先有"有新版"数据源(内置目录), 且和"磁盘占用"联动时
才真正闭环。

**现状**: 三个"磁盘意识"缺口捆在一起——① 页面每个模型单独显示 size(`models_view.js` 第 623 行主行、第 712 行

**对比**: 成熟产品在"存储/磁盘"页给总占用; 下载器在开始前提示"磁盘空间不足"; 下载完成的文件不会显示 0 大小。

    确认框提示(~8 行); 自定义模型在 `_finishDownload` 里把下载轮询拿到的 `total` 写进 register 的 size_bytes

**建议权重**: 中(A 的①③高、②中)—— 三个都是"磁盘意识"一类, 单看都小, 打包做性价比最高; ② 涉及大文件
下到一半才失败的坏体验。
