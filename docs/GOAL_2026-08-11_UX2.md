# F 系列(P0)手机端同步跑通最后一跳

A1 确实修好了 —— 桌面端实测「本次推 1421 条」。但**手机端仍然显示 0**,
逐层排查后发现是**服务端被污染 + 手机端合并 O(n²)** 两个新问题,与 A1 无关。

## 实测证据(不是推测,是拿 token 直接 GET 服务端拉回来的 1.0 MB 响应)

```
GET https://sync.viiyd.com/v1/sync?since=0     → 200, 1,005,944 bytes, 3.4s
ok=True  rev=4268  deck_exists=True  changed=2845
stages: {'new': 1424, 'review': 1288, 'mastered': 133}
```

**服务端有 2845 条,不是 1421 条**:

| 组 | 条数 | 特征 | 来源 |
|---|---|---|---|
| 真实词 | 1421 | `word='hieroglyphics'` 等,stage=review/mastered,全部已到期 | 桌面端 08-11 09:20 推送 |
| **测试 fixture** | **1424** | `word='w0'…'w1423'`, `meaning='含义0'`, stage=new, next_review=null | **验收脚本打到了生产 VPS** |

两组 lemma **零重叠**(1424 + 1421 = 2845 unique),所以互不覆盖、共存。
桌面本地库干净(`data.db` 1424 行,`updated_at=0` 的 0 行),污染只在服务端。

## F1(P0)手机端合并是 O(n²) —— 这是"显示 0"的直接原因

`cloud/mobile/app-logic.js:95`:

```js
for (const remote of pullRes.changed || []) {
  const existing = await storage.getWords();   // ← 全表扫描在循环内
  const local = existing.find((w) => w.lemma === remote.lemma) || null;
  if (...) { await storage.putWord(remote); }  // ← 每条一个独立事务
}
```

2845 条 → 约 **400 万次行反序列化 + 2845 个独立 IndexedDB 事务**。
`cloud/mobile/app.js:489` 的 `boot()` 是 `await app.sync()` **然后才** `await loadEntry()`,
同步没返回 → `loadEntry` 永不执行 → 页面停在 HTML 初始值 **0**。

**关键**:这不是"失败",是"没返回"。所以 A3 的错误提示帮不上忙 —— 它只在 `!ok`
或 `catch` 时才显示。用户看到的 0 是静止的初始值,不是算出来的结果。

**修**:`getWords()` 提到循环外建 `Map<lemma, entry>`;`putWord` 逐条改成一次
`setWords` 批量事务(`adapter.js` 已有 `setWords`,复用,不新写)。
**验收**:1421 条合并 < 1 秒(测试打点计时,写进提交信息);
2845 条(含 fixture)也必须完成而不是挂起。

## F2(P0)页面不许被同步阻塞

`boot()` 改成**先 `loadEntry()` 渲染本地已有数据,再后台 sync,完成后重渲染**。
同步期间 chip 显示「同步中 N/M」——**静止的 0 不允许再出现**:
要么是算出来的 0(且 chip 显示"已同步"),要么明确显示进行中/失败。

**验收**:断网打开 → 立即显示本地词库,chip 显示离线原因;
首次配对打开 → 先显示 0 + 「同步中」,拉完自动变成真实数字。

## F3(P0,纪律)验收测试禁止指向生产端点

这次污染的根子:**验收脚本用真实域名跑,1424 条 fixture 落进了用户生产库**。
生成它的脚本还不在仓库里(临时跑的),这本身也是问题 —— 仓库里的
`cloud/worker/test/local_test.mjs:259` 有同名 1424 词 fixture,那份是打本地的。

- 加门禁项 `test:no-prod-endpoint`:`cloud/**/test/**`、`scripts/**` 里出现
  真实域名(`sync.viiyd.com`、`*.pages.dev`、`*.workers.dev`)直接**门禁失败**;
  只允许 `127.0.0.1` / `localhost` / 临时 `KV_DIR`。
- 一次性验证脚本也必须入库(否则没人能复现、也没门禁能管到它)。

**验收**:门禁新增项全绿;故意在测试里写一个真实域名 → 门禁必须红。

## F4(P1)服务端数据丢了也要能强制重推

A1 只在 **endpoint 变化**时全量重推。清完服务端后 URL 和 user 都没变 →
`endpoint_key` 匹配 → **不会重推**。A2 能检测 `deck_exists=false` 并警示,但没有动作。

设置页加「强制全量重推」(清本 user 的 `sync_state` 行);
`deck_exists=false` 时警示文案直接引导到这个按钮。
**验收**:手动清空服务端 → 点强制重推 → 显示「本次推 1421 条」。

# H 系列(P1)生词本 / 背单词合并 —— 设计稿本来就是合的

## H1 合并成一个「生词本」tab,背单词是它的模式而不是兄弟 tab

## H2 撤销条位置错了 —— 这是"影响专注"的机制

设计 §01b 原话:评分后「3 秒内可撤销,**撤销条压在顶部进度条下方**」。
现状 `app.css:620`:`position: fixed; bottom: 24px; left: 50%` + `elevation-2` 的
**深色药丸浮在底部正中** —— 正好落在评分完视线回落的位置,每评一张弹一次。

**改**:占位常驻(不出现/不消失/不位移),3 秒内可点、之后转灰失效。
**动效只允许透明度,不允许位移** —— 周边视野里的运动才是分心源,
不是"有个撤销按钮"这件事本身。键盘补 `Ctrl+Z` / `Backspace`,不用鼠标的人根本不用看它。

**位置要落到桌面端的等效位置,别机械照搬**:设计原话「压在顶部进度条下方」出自
**§01b 手机端**(手机是单列,顶部就是进度条)。桌面端是三栏,进度条在**左栏队列头部**
——把撤销条放那儿等于放到视线之外。桌面端应放在**中间卡片区的正上方**(评分动作的
正上方,视线自然落点),保持"常驻不位移"这条本质规则。这属于**有意的等效落位,
不是偏离**,写进 `DESIGN_CONFORMANCE.md`。

详情里还有「在阅读器中打开」和**「N 处出现」多例句**。

- 行压缩成单行:`词 · 释义 · 阶段 · 到期`,原句默认收起(点行展开)。
- 满宽删除按钮撤掉,维护动作收进行尾的 `⋯` 菜单:
  **移出生词本 / 标记已掌握 / 编辑释义 / 在阅读器中打开**。
- 补**批量选择**(勾选 → 批量移出 / 批量标记已掌握)。理由见 H4:没有批量,
  1424 词的库根本没法收拾。
- 「已掌握」默认不在「全部」里占位(设计的筛选本就把它单列)。

## H4(重要)今日队列 323 分钟 = 这个功能现在没法用

截图实测:**今日队列 1291 词,预计 323 分钟**。5.4 小时,没有人会开始。

根因不是算法错,是**决策前提变了**:「到期复习不封顶」(`GOAL_STAGE_SRS.md` 三项已定②)
的前提是**日常增量**,而实际是一次性导入 1424 词的**存量**,全部 `next_review`
都在过去(实测最晚 2026-08-04)。不封顶遇上存量,第一天就是 5.4 小时。

**修**:首次导入/迁移进来的词做**存量打散** —— 按加入顺序把 `next_review` 摊到未来
N 天(N 由 每日可承受量 推出,如每天 40 词 → 36 天),而不是全堆在今天。
今日队列另加**可见的每日上限**与「剩余 N 词顺延到明天」的明确文案。

**前置依赖:必须先做 H5(剔词)再做 H4(打散)。** 反过来就是先给一批马上要删的词
排好了日程,打散结果作废还得重排。
**这两条都要先于 H1/H3** —— 那两条是好不好用,这两条是能不能用。

## H5 词表里混着 either / lead / confirmed 这类词

截图里的实际条目:`either`(任一)、`lead`(引导)、`confirmed`、`repeatedly`。
成人自读档案把 `either` 收进生词本,说明**划词入库没有词频门槛**。
5.4 小时里有相当比例花在背 `either` 上 —— 这会直接毁掉用户对这个功能的信任。

- 词表提供**按词频批量剔除**(如"剔除最常见 3000 词"),一次性收拾存量。
- 入库侧加档案相关的词频门槛(成人自读 vs 儿童取值阈值不同),**默认不拦、只提示**,
  避免把用户真想学的词悄悄吃掉。
- 顺带核对:设计的 `word_key = 词头小写 + 词性`,而 `confirmed` 是以屈折形入库的。
  确认词表展示与 `word_key` 归一是否一致(实测 1421 条里 903 条 `word == lemma`),
  **不一致就会出现同一个词两条复习状态**。先查证再改,别直接动归一规则。

## H 系列验收

顶栏两项;`review` 路由重定向可用;专注模式下顶栏/词表不可见,`Esc` 退出且进度保留;
撤销条在顶部进度条下方、常驻不位移;词表单行高度 ≤ 56px;批量选择可用;

# K 系列 查词失败 + 在线 AI 作为离线的兜底(不是替代)

起因:阅读器点 `doorway` 查词,面板显示
**「doorway 的词义查询失败 (模型已配置但未返回结果)」**,来源「本地词典」。

## K1(P0)真实错误在最后一米被丢掉了

`commands/reader.rs:26-42`:

```rust
if let Ok(v) = dict_daemon::lookup(&prep_path, &llm_model, w, ctx) {
    if let Ok(parsed) = daemon_result_to_tuple(&v) { return Ok(parsed); }
}
return Ok((... format!("{w} 的词义查询失败 (模型已配置但未返回结果)") ...));
```

`dict_daemon::lookup`(`infrastructure/dict_daemon.rs:104`)本来会给出**六种各不相同的
具体原因**:「词典守护注册表被占用」/ spawn 失败 /「写词典守护请求失败: {e}」/
「读词典守护响应失败: {e}」/「词典守护进程已退出」/「词典守护响应非法: {e}」,
外加侧车自己返回的 `error` 字段。

**两个 `if let Ok` 把这六种全丢了**,统一成一句话。而且这句话在多数分支下**是错的** ——
比如"响应非法":侧车明明返回了,只是解析不了,却说"未返回结果"。
**信息是有的,是代码把它扔了。**

**修**:`match` 取代 `if let Ok`,把真实错误串接到面板文案与 `aidulc.log`;
解析失败与调用失败**分开两句话**(一个是"侧车没回",一个是"回了但看不懂,已记日志")。
先做这条 —— **不修它,后面所有关于"为什么失败"的判断都是猜的**。

## K2(P0)`word_lookup` 是同步命令 + 无超时阻塞读 —— S0 的遗漏项

`commands/reader.rs:11` 是 `pub fn word_lookup`(**同步** `#[tauri::command]`,跑主线程),
而 `dict_daemon.rs:132` 是**无超时的 `read_line`**,还持着全局 `registry()` 锁。
侧车挂死 → 主线程永久阻塞 → **整窗假死,和设置页那次 S0 是同一个病**,
而且这条在**热路径上**(每点一个词都走)。

`GOAL_STAGE_UX.md` 的 S0 卡明写了「**同时排查其余同步命令里有没有同类阻塞调用 ——
这是根子上的问题, 不只这一处**」。这一项**没有做**,`word_lookup` 就是漏网的那条。

**修**:① `word_lookup` 改 `async` + `spawn_blocking`(照抄 S0 对 `components_health` 的做法);
② `dict_daemon` 的读响应加超时(复用 `services/components.rs::read_stdout_with_timeout`
的 `recv_timeout` 模式,**别新造一套**),超时即 kill 守护并返回明确错误;
③ **顺便把剩下的同步命令扫一遍**,凡是 spawn 子进程 / 阻塞读 / 网络请求的一律同样处理,
在报告里列出扫描结果(哪些查了、哪些改了),不要再漏。

## K3 在线 AI 兜底:按**外发粒度**授权,不是按功能开关

**先承认一处判断修正**:本文档 J5 原稿把"接在线 API"整体描述成"整章正文发给第三方",
**那是把粒度拍平了**。用户指出:在线 AI 本就是**补齐离线的不足**,查词只发一个词加一句
上下文,和整本外发完全不是一回事。这个修正是对的,K3 按它重写。

**授权按粒度分三档,不是一个总开关**:

| 用途 | 外发内容 | 量级 | 默认 |
|---|---|---|---|
| **查词** | 1 个词 + 所在那 1 句 | ~200 字符 | 配了 key 即可用,失败时就地提示 |
| **单句讲解 / 核对翻译** | 该句(至多带前后各 1 句) | ~500 字符 | 同上 |
| **整本翻译 / 整本讲解** | 全书正文 | 数十万字 | **默认关闭,每本书单独确认** |

前两档是"一次一句、用户点了才发",风险与收益完全不对称,不该被第三档的顾虑拖住。
第三档才是真正意义上的"书离开了本机",维持严格确认。

**触发时机:失败即就地给出口,不是藏在设置里**
- 查词失败 → 面板里直接出现「**用在线 AI 查一次**」;未配置则「去设置配置在线引擎」。
- 某句讲解缺失 / 翻译存疑 → 该句支撑区出现「**在线核对这一句**」。
- 整本处理因模型缺失失败 → 处理中页给「改用在线引擎重试」(走第三档确认)。

**三条硬约束**
1. **绝不自动回退。** 本地失败**必须**由用户点一下才发出去 —— 自动重试等于静默外发,
   用户根本不知道数据出去了。
2. **绝不由作者的服务器代理转发。** 用户填自己的 key,从自己机器直连服务商,
   作者不在链条里。(这条 K3 保留 J5 原判断,是整个架构一直在守的东西。)
3. 每次外发前,UI 上能看到**这次发什么**(查词就显示"将发送: doorway + 该句"),
   不做"你已同意过"的一揽子授权。

**实现复用**:HTTP 客户端与重试沿用 `infrastructure/sync_v1_client.rs` 的既有模式;
key 存 Credential Manager(`services/credentials.rs`);
在线引擎作为 `model_registry` 里的一种 `source_type`(不新起一套模型概念)。

## K 系列验收

K1:构造四种失败(守护起不动 / 中途 kill / 返回非 JSON / 返回 `ok:false`)→ 面板与日志
给出**四种不同**的原因文案,没有一种说成"未返回结果";
K2:注入永不响应的假守护 → 查词在超时内返回错误且**窗口全程 Responding**(照 S0 那条
单测的写法);报告里列出同步命令扫描结果;
K3:未配置在线引擎时失败面板显示"去配置";配置后点「用在线 AI 查一次」能拿到结果;
**断开网络不影响本地查词**;整本外发有单独确认;全程无自动回退(单测断言:本地失败
时不发起任何网络请求)。
