# 备料速度优化方案(2026-08-16)

用户反馈"太慢了"。本文是**实测数据 + 方案选项**,不是已定方案——每条标注预估收益/
风险/改动量,由用户拍板选哪些做。

## 一、实测数据(2026-08-16 探针 + checkpoint 统计)

硬件/模型:RTX 3060 12GB · Qwen3-4B-Instruct Q4_K_M(2.4GB)· llama_cpp_python 0.3.34

跑书期间 GPU 状态:利用率 81-87%,功耗 142W/170W,显存 7.9GB/12GB,温度 80°C
→ **GPU 在满负荷工作,不是空转,也没有降频/热限制**。

| 项目 | 实测值 | 样本 |
|---|---|---|
| explain 单次调用耗时 | 平均 **7.44s**(3.34~10.44s) | n=13,ch1 |
| translate 单次调用耗时 | 平均 **0.26s** | n=4(batch_size=1 补漏) |
| explanation 输出长度 | 中位 **402 字符**,均值 408,p90 528,max 1146 | n=2410 |
| translation 输出长度 | 中位 **15 字符**,均值 18 | n=3999 |
| nlp 阶段 | 140 句 / 166 秒 | 本次续跑 |

## 二、关键结论

**耗时几乎完全正比于"生成的 token 数",跟调用次数关系不大。**

对照两个比值:
- 输出长度比 explain:translate = 408 : 15 = **27 倍**
- 耗时比 explain:translate = 7.44 : 0.26 = **28.6 倍**

两者几乎完全吻合。这说明单次调用的固定开销(prompt 处理、请求往返)占比很小,
**时间基本都花在"一个 token 一个 token 地吐字"上**。

### 更正一处此前的判断

我 8-15 说过"explain 批量化(像 translate 一样一次塞 15 句)是最大杠杆",
**这个判断被实测否定了**。批量化只能省掉每次调用的固定开销,而固定开销本来就很小;
一次塞 15 句,模型仍然要为这 15 句各写一段 400 字讲解,**生成的总 token 数不变,
总时间也就基本不变**。批量化预估只有 10-20% 收益,不是我原先以为的数量级改善。
以实测为准,原判断作废。

### 另一处需要如实说明:我 8-15 修的 bug 让它变慢了

那次修的是"深讲解被 max_tokens=400 截断导致 JSON 解析失败"(2983/7357 句失败),
修法是把预算提到 700(失败再用 1100 重试一次)。副作用是:模型本来就想写 400 字
左右(中位 402 字符正好顶着旧的 400 token 上限——这也正是当初大量截断的原因),
预算放宽后它会写得更长,**单次调用从约 5s 涨到实测 7.44s**。

- 上次全书 ≈ 7357 句 × 约 5s ≈ 10 小时(与实际观测的 10.5 小时吻合)
- 按现在的 7.44s 线性外推 ≈ **15 小时**

也就是说,"不被截断"和"快"这两件事,目前是用 max_tokens 这一个旋钮在对赌。
**但这是个假两难**——见方案 A。

## 三、方案选项

预估耗时均按"7357 句 × 单句耗时"线性外推,基于实测 tok/s,标注为估算而非实测。

### 方案 A:压缩讲解长度(改提示词)—— 收益最大、风险最低

`prompt.py` 的 `EXPLAIN_DEEP` 现在写的是"讲得啰嗦一点没关系,多用打比方",
模型照做,每句吐 400 字。改成明确限定字数(如"讲解控制在 120 字以内,只点破
最关键的一处")。

- **预估**:输出 400 字 → 120 字,单句 7.44s → 约 2.5s,全书 **15 小时 → 约 5 小时**
- **附带好处**:输出远低于 700 预算,**截断问题从根上消失**,那条重试基本不会触发
  (重试本身也要 7s+,少触发一次省一次)
- **改动量**:改几行提示词字符串
- **风险**:纯产品取舍——每句 400 字的讲解 vs 120 字,哪个对"陪小孩读"更好?
  400 字对逐句阅读来说其实是一堵墙。**这条要用户拍板,不是技术判断**

### 方案 B:不是每句都讲(加难度筛选)—— 收益与 A 可叠乘

现在 deep 策略对**每一句**都生成讲解,包括 "He went to the bank." 这种。
可以只对"有生词/长难句/特殊语法"的句子讲,其余跳过。

- **预估**:若只讲 30% 的句子,时间再 ÷3。与方案 A 叠加后 ≈ **1.5-2 小时**
- **改动量**:中等——要定"什么算难句"的判据(可复用 nlp 阶段已有的分词/词频数据,
  项目里已经有 `ADULT_COMMON_TOP_N` 这类词频门槛的先例)
- **风险**:判据定不好会漏掉该讲的句子。建议做成 profile 可调而不是写死

### 方案 C:投机解码(speculative decoding)—— 纯技术加速,不改输出

已确认 `llama_cpp_python 0.3.34` 的 `Llama(draft_model=...)` 参数**可用**。
用一个小模型(如 Qwen3-0.6B)起草、大模型批量校验。

- **预估**:典型 1.5-2.5x。**输出分布严格不变**(投机解码是数学上等价的加速,
  不是近似),讲解质量零损失
- **改动量**:中等——要下载 draft 模型 + 改 `server.py` 的构造 + 显存要多占约 0.5GB
  (现在 7.9/12GB,放得下)
- **风险**:draft 模型选不对可能反而变慢(接受率低);需要实测验证
- **说明**:这条与 A/B 完全正交,可以叠加

### 方案 D:并行解码(continuous batching)—— 理论收益大但此路不通

单条流式解码是**显存带宽瓶颈**(每吐一个 token 要把 2.4GB 权重读一遍),
并行跑多条序列能把权重读取摊薄,理论上 3-5x。

**但实测确认 `llama_cpp_python 0.3.34` 的 `Llama` 高层 API 不暴露
`n_parallel`/`cont_batching`/`n_seq_max`**。要用只能回到 llama-server 子进程模式,
而 `server.py` 的注释记录了当初正是**从 llama-server 换到进程内库**的
(原因是自带的 llama-server.exe 是 CPU build,17 t/s vs 进程内 CUDA 的 68-80 t/s)。
重新走回去要自己解决 CUDA build 的 llama-server + 孙进程治理。

- **结论**:**本轮不建议做**。收益虽大,但改动面和风险远超 A/B/C,且踩过一次坑

### 方案 E:换更小的模型 —— 有效但有质量代价

4B → 1.7B 约 2x,→ 0.6B 更快。

- **风险**:讲解质量直接下降,与产品定位冲突。**建议只作为 C 的 draft 模型用途**,
  不作为主模型

### 方案 F:开 flash_attn —— 顺手做,收益小

`server.py` 构造 `Llama` 时 `flash_attn` 用的是默认 `False`。开启通常小幅提速、省显存。

- **预估**:个位数百分比,不解决主要矛盾
- **改动量**:一行;**风险**:需实测确认不影响输出

### 方案 G:批量化 explain —— 优先级下调(见"更正")

- **预估**:仅 10-20%,不是数量级改善
- **建议**:等 A/B 落地后再评估还值不值得做

## 四、建议顺序

1. **先补一个探针**(零风险,10 分钟):现在的 TIMING 行只记时间不记 token 数。
   把 llama 返回的 `usage.completion_tokens` 也记进去,就能算出**精确的 tok/s**,
   彻底确认"生成占比"到底是 90% 还是 60%,以及方案 A 的收益能否线性兑现。
2. **方案 A**(改提示词)——收益最大、改动最小、顺带消灭截断问题。**但需要用户先
   拍板"每句讲解要多长"**,这是产品决策不是技术决策。
3. **方案 B**(难句筛选)——与 A 叠乘,是把 15 小时压到 2 小时以内的关键第二步。
4. **方案 C**(投机解码)——A/B 落地后如果还想再快,且不愿再牺牲讲解内容,走这条。
5. F 顺手验证;D、E、G 本轮不做。

## 五、验收标准(机械可核对)

任何一条落地后,用**同一本书、同一批句子**跑一次,从 `run.log` 提取:

```bash
grep "TIMING stage=explain" run.log | sed -E 's/.*elapsed=([0-9.]+)s/\1/' \
  | awk '{s+=$1;n++} END {printf "n=%d avg=%.2fs\n", n, s/n}'
```

- 方案 A 验收:`avg` 从 7.44s 降到 **≤3.0s**,且 `attempt=2`(重试)的行数
  占比 **<2%**(现状是截断重试的主要来源)
- 方案 B 验收:`n`(实际调用次数)相对总句数的比例降到目标区间,且
  跳过的句子在 `quality_report.json` 里**不被记为 failed**(跳过 ≠ 失败)
- 方案 C 验收:`avg` 相对同配置基线下降 ≥30%,且**随机抽 20 句人工对比讲解内容**
  与基线无实质差异(投机解码应当输出等价)

## 六、本文档的不确定性(如实标注)

- 所有"预估耗时"都是**基于实测 tok/s 的线性外推**,不是实测结果。生成速度随
  上下文长度增长会略降,实际可能比估算差 10-20%
- explain 的 13 个样本全部来自 ch1,样本量小;不同章节句子长度分布可能不同
- 402 字符的中位数来自**旧配置(400 token 上限)下成功的句子**,新配置(700)下
  模型会写多长尚未统计——这也是建议先补 token 计数探针的原因
