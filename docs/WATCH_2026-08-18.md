## 新发现 2(真 BUG): `nlp_realign` 被算进"失败句数", 用户看到的失败数被放大几十倍

`quality_report.json` 的 `failedSentences` 里混进了 `nlp_realign` 这一类条目。看源码
[`prep/aidulc_prep/pipeline/nlp/stage.py:88`](../prep/aidulc_prep/pipeline/nlp/stage.py) —— 它**根本不是失败**,
是 checkpoint 位置冲突时"已清空该位置历史阶段数据强制重跑, 防止张冠李戴"的**正常记账**,
恰恰是保护数据正确性的机制。但它走的是 `quality.add_failure(...)`, 于是:

| 书 | `failedSentences` 长度(= UI 显示的失败句数) | 其中 nlp_realign | **真实失败** |
|---|---|---|---|
| Wild Robot | **9023** | 8784 | **239** |
| Wonder | **5551** | 5321 | 230 |
| Holes | 3074 | 2893 | 181 |
| Number the Stars | 2757 | 2556 | 201 |
| Hatchet | 2528 | 2474 | 54 |
| Despereaux | 1390 | 1255 | 135 |
| Frindle | 1245 | 1209 | 36 |
| Winn-Dixie | 899 | 792 | 107 |
| Tuck Everlasting | 154 | 0 | 154 |
| Charlottes Web | 35 | 0 | 35 |

传播路径(全部读的是 `failedSentences.length`, 没有按 stage 过滤):
- [`reader/views/prep_view.js:438`](../reader/views/prep_view.js) → 任务详情弹窗的「失败句数」
- [`src-tauri/src/application/library_service.rs:26`](../src-tauri/src/application/library_service.rs) → 书库卡片的失败句读数
- [`src-tauri/src/application/job_orchestrator.rs:1216`](../src-tauri/src/application/job_orchestrator.rs) → 人话失败原因里的句数和 stage 列表(所以摘要写成
  "9023 句有部分阶段失败 (align, explain, **nlp_realign**, translate, tts)")

注意 `stages` 那一栏的 successRate **是对的**(nlp_realign 没进 `stages`), 错的只有
`failedSentences` 这条列表和从它派生的一切。也就是说:**阶段成功率可信, 「失败句数」不可信**。

为什么 Charlottes Web / Tuck 是 0: 这两本是"从讲解"重跑, nlp 阶段压根没跑, 自然没有
realign 记账 —— 反过来印证了这批条目就是"解析变了 → 清 checkpoint"留下的痕迹,
8/17 那轮改了 EPUB 行内标签解析, 几乎每句原文都变了, 所以近乎全量记账。

**本轮不修**(只读观察)。修法有两条路, 等这批跑完再定:
(a) `nlp_realign` 不进 `failedSentences`, 单开一个 `realigned` 计数;
(b) 保留在列表里但所有消费方按 stage 过滤掉它。
倾向 (a) —— 语义上它就不是失败, 留在失败列表里迟早还会被下一个消费方读错。
