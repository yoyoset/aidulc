# GOAL 2026-08-16 STDIMPORT — 源书统一标准 + 重跑入口重构 + 导入侧把关

用户拍板方案(2026-08-16):先手动把已导入的源书做统一标准处理并分书决定怎么重跑,再改
重跑入口逻辑(重跑前面加"重新设置"),最后把同一套标准接进导入路径(缺依赖补依赖,不达标给
警告)。本文件是**评审用方案,不含代码改动**;通过后由 loop + Haiku 4.5 执行。

## 0. 先说三条实测结论(方案建立在这三条上,不是推测)

1. **`book_id` = 文件名 + 档案 id**(`commands/library.rs:135 book_id_from_path`)。换一个档案
   id 去创建译本 = 系统眼里的另一本书 = 全新 `pack_dir` = 全新 checkpoint 目录 = **全本重跑,
   旧成品原样保留**。用户说的"档案加 BK,认不到就重跑了"成立,机制就是这条。
2. **章节结构变化不需要人工判断重跑范围**。`nlp/stage.py::reconcile_position_checkpoint`
   会拿旧 checkpoint 里的 `original_text` 跟本次重新解析出的同位置句子比对,不一致就整条清空
   (`overwrite_sentence`),该句的 translate/explain/tts/align 全部自动重跑。所以"章节错乱"
   这类结构性修复,选**范围=自动**即可,不必手工选"全部"。
3. **只改章节标题的修复几乎零成本**。标题变了但句子文本没变 → 每句 checkpoint 都命中 →
   parse 重跑、nlp/translate/explain/tts 全部跳过、pack 用新标题重写一遍。今天第 4 条
   `(Untitled)` 那类修复属于这一类。反过来,**章节数量变化**(多切/少切一章)会让后面所有
   章节的位置整体错位,判据 2 会把它们全部判为不一致 → 实际接近全本重跑,这是无法避免的。

## 1. "统一标准"的定义(机械可核对,6 条)

一本源书通过下面 6 条即为**达标**,任何一条不过即为**不达标**,只在第 2/5 条给警告不阻断:

| # | 判据 | 数据来源 | 不过的后果 |
|---|---|---|---|
| S1 | 能作为 zip 打开且有 OPF/spine | `load_epub_with_spine_health` | 阻断 |
| S2 | 真缺失文件数 = 0(URL 解码后仍读不到) | `_classify_uncovered_epub_files` | >10% 阻断,否则警告 |
| S3 | 章节数 ≥ 1 且总句数 ≥ 50 | 解析结果 | 阻断 |
| S4 | 句数分布无离群章 | `core/health.py::detect_anomalies` | 警告 |
| S5 | `(Untitled)` 章节占比 ≤ 20% | 解析结果 | 警告 |
| S6 | 前后言条目未混进正文章节 | `NON_BODY_TOC` | 警告 |

这 6 条同时是:手动体检脚本的输出列、导入时警告的判据、以后回归测试的断言。**一处定义,
三处复用**,不允许各写各的。

## 2. 第一步:手动统一标准处理(本轮先做,不改产品代码)

- 写一次性脚本 `scripts/audit_sources.py`(放 `scripts/`,不进 `prep/` 包,不进打包),对
  `books` 表里所有 `kind=original` 的 `source_path` 逐本跑 S1–S6,输出一张表:
  书名 / 章数 / 句数 / 真缺失 / Untitled 数 / 离群章 / 判定(达标·警告·不达标)。
- **不改写源 EPUB 文件本身。** 用户说的"把原本做统一标准处理",我建议实现成"体检 + 分类",
  不实现成"重写 zip"——重写 EPUB 是有损且不可逆的,而今天已经确认真正的标准化逻辑(URL 解码、
  前后言过滤、标题回退)全部落在**解析层**,源文件保持原样就能得到标准结果。若坚持要产出
  标准化副本,退路是写到 `<pack_root>/normalized/xxx.std.epub`,原文件只读不动——但这一步
  除了占磁盘没有额外收益,建议不做,等到确实遇到"解析层修不了、必须改文件"的书再说。

## 3. 第二步:分书处置(手动,不改代码)

按第一步的表分三类:

- **不达标(结构错/大量丢失)** → 新建一个档案,名字后缀 `BK`(id 也不同,例如
  `default-bk`),用它走"创建译本" → 因判据 1 生成新 `book_id`,**全本重跑**,旧的留着对比,
  确认新版正确后再在书库删旧的。
- **仅警告(标题/前后言类)** → 不换档案,原地重跑,范围选**自动**;按判据 3,这类基本只
  重跑 parse+pack,几分钟内完成。
- **达标但讲解太啰嗦** → 只改档案里的 K33 两个新字段(讲解字数上限/触发门槛),重跑范围选
  **从讲解**,不动翻译和语音。

这一步我手动执行并把每本书的分类结论写进 `memory/pipeline.md`。

## 4. 第三步:重跑入口重构(代码,loop 执行)

**现状(实测)**——语义重叠的入口有 3 个,分散在 2 个页面:

| 位置 | 按钮 | 实际行为 |
|---|---|---|
| `prep_view.js:279` | 重跑… | 改模型 + 选范围 → `retryCustom` |
| `prep_view.js:283` | 重试失败句 | 等价于「重跑… + 范围=自动 + 不改模型」→ `retryFailed` |
| `library_view.js:569` | 重新生成译本 | 成品文件缺失时走创建译本流程 |

**目标**——收敛成"一个入口、两段式"的对话框,按钮统一叫**「重新处理…」**:

1. **第 1 段:重新设置**(用户要的"重跑前面加重新设置")——模型(LLM/TTS/NLP,现状已有)
   + **学习档案(新增)** + 语言。默认全部"保持当前",不改就是纯重跑。
2. **第 2 段:重跑范围**——沿用现有 5 档(自动/从翻译/从讲解/从语音/全部),但把文案改成
   跟第 1 段联动的推荐:改了档案里跟讲解相关的字段 → 默认高亮"从讲解";改了 TTS/音色 →
   默认高亮"从语音";什么都没改 → 默认"自动"。**只是默认值,用户仍可自选。**

「重试失败句」不删,降级成对话框里的一键快捷方式(= 不改设置 + 范围自动),不再单独占一个
顶层按钮——三个按钮并排是当前混乱的直接来源。

**必须在评审里拍板的一个取舍**:重跑时换档案,`book_id` 里已经烧进去的档案段怎么办?

- 方案 A(推荐):`book_id` **不变**,只把新档案写进 `job_request.profile` 和 `editions`
  的参数快照。代价是 `book_id` 里的档案段退化成"创建时的档案"这个历史标签,不再是当前值。
- 方案 B:换档案就当成新书(等于第 3 节的 BK 手法),旧成品保留。语义干净,但用户每换一次
  档案就多一本书,书库会膨胀。

我倾向 **A**:用户的原话是"我点击修复,可以重新选模型和档案,然后重跑,这样我只用重跑讲解"
——这个诉求本身就是"就地改,不要变成另一本书"。B 已经由第 3 节的手动 BK 流程覆盖了。

## 5. 第四步:导入侧(代码,loop 执行)

**现状(实测)**:`job_orchestrator.rs::register_import_batch` 只往 `books` 表写一条
`status=pending` 的记录,**完全不碰文件内容**;所有校验都在 `batch_start_prep` 之后、
真正跑 `Runner._parse()` 时才发生。所以现在一本坏书可以"导入成功",等点了创建译本才报错。

改成:

1. **导入时跑 S1–S6 体检**(新增一个 Rust command,调侧车 `cli.py --preview-book` 已有的
   健康检查路径,不引入第二套解析实现)。
2. **结果分三色回给前端**:达标(直接入库)/ 警告(入库,书卡上挂一个黄色标记 + 悬停显示
   具体哪条判据没过)/ 不达标(**不入库**,弹窗说明原因,给"仍然导入"的强制选项)。
3. **依赖检查前移**:现在模型/ffmpeg 等前置检查在 `batch_start_prep`。导入时也跑一遍
   (只读、不阻断),缺什么在导入结果里一并提示,让用户在真正开跑前就知道要补什么。
4. **性能兜底**:体检要完整解析一遍 EPUB,大书几秒级。批量导入必须**并发 + 带进度条**,
   且体检失败(超时/异常)一律降级成"警告"放行,不能因为体检本身出问题就挡住导入。

## 6. 明确不做

- 不重写源 EPUB 文件(理由见第 2 节)。
- 不做"导入时自动修复"——只体检 + 提示,修复仍然在解析层。自动改用户的文件不可逆。
- 不动 `book_id` 的生成规则(方案 A 的前提就是不动它);真要去掉档案段是独立的更大改动。
- 不合并 `library_view` 的"重新生成译本"入口——那是成品文件丢失的补救路径,和"重跑备料"
  不是一件事,合并会让两个都变模糊。
