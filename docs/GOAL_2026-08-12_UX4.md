# M0(P0,最高优先)手机端一个词都没有的**真正**原因:IndexedDB 用法错误

**这是贯穿 F1/L0 全过程的真凶。之前定位的 O(n²)、服务端污染、未部署都是真实问题,
但都不是"显示 0"的直接原因 —— 修完它们仍然是 0。**

## 实测证据(2026-08-12,干净浏览器,非用户机器)

打开线上配对链接 → 仍显示 0。**排除 Service Worker 缓存**(全新浏览器无旧 SW)。
控制台两条错误:

```
Uncaught (in promise) InvalidStateError:
  Failed to read the 'result' property from 'IDBRequest': The request has not finished.
    at app.js:82   (updateSyncChip → getToken)
    at app.js:490  (boot)
```

服务端同时刻实测正常:`GET /v1/sync?since=0` → 200,2845 条,rev 4270;
其中**真实词 1421 条,今日到期 1419 条**。数据一直都在。

## 根因(线上与本地代码一致)

`cloud/mobile/adapter.js` 的 `browserAdapter`:

```js
function getAll(store) {
  return tx(store, 'readonly', (os) => {
    const r = os.getAll();
    return r.result;      // ← IDBRequest 尚未完成就同步读 .result → InvalidStateError
  });
}
```

`os.getAll()` 返回的是 **IDBRequest**,必须等 `onsuccess` 才能读 `.result`;
当场读必抛 `InvalidStateError`。`getMeta()`(`getToken`/`getWorkerUrl`/`getDeviceName` 的底座)
是同一个写法,同样抛。

**后果**:写入正常(`put` 不需要读 result),**所有读取一律失败** →
`getToken()` 抛 → 同步根本没发起;`getWords()` 抛 → 词表恒为空。
**手机端从上线第一天起就没能从 IndexedDB 读出过任何东西。**

## 为什么所有测试都是绿的

`cloud/mobile/test/app_test.mjs` 全部用 **`nodeAdapter`**(纯内存实现),
**真正发货的 `browserAdapter` 零测试覆盖**。F1 报告的"1421 条合并 2ms"
测的是内存 Map,不是 IndexedDB。

这是教训 3(玩具数据)与教训 8(测内部不测可见结果)最彻底的一次:
**被测的实现和被发货的实现根本不是同一份代码。**

## 修

1. `tx()` 改成等请求完成再取值 —— `fn` 返回 IDBRequest,由 `tx` 在
   `req.onsuccess` 取 `result`、在 `t.oncomplete` resolve;`getAll`/`getMeta` 一并改。
2. **`browserAdapter` 必须有测试**:引入 `fake-indexeddb` 跑同一套
   `app_test.mjs` 用例(至少覆盖 存词→读回→getToken→sync 全链路)。
   **不允许再出现"只测 nodeAdapter"的状态。**
3. 修完 bump 版本并部署(L0 的流程),**部署后用干净浏览器复验并贴控制台截图**。

**验收**:干净浏览器打开配对链接 → 今日待复习显示**非 0**(当前服务端数据下应为
1419 到期 + 新词配额);控制台无 `InvalidStateError`;`fake-indexeddb` 用例在门禁里。

# 零之二、反馈契约(本轮真正的主线,优先于任何单张卡)

**站在"完全不了解这个软件的用户"的位置上看,这八轮抓到的所有问题是同一个形状:
软件知道发生了什么,但没告诉用户。**

| 现象 | 软件内部知道 | 用户看到 |
|---|---|---|
| 同步推了 0 条 | `wrote=0`、`deck_exists=false` | 「已同步」 |
| 查词失败 | 六种各不相同的具体原因 | 一句"未返回结果"(还是错的) |
| 成品文件没了 | `pack_dir` 不存在 | 「已就绪 · 20 章」 |
| 点译本/开始复习/更改目录 | 事件收到了 | **什么都没有** |
| 扫描模型 | 扫了哪个目录、找到什么 | 一句 toast |
| 手机端 IndexedDB 全部读失败 | 抛了 `InvalidStateError` | 一个安静的 0 |

**所以本轮不是修 7 个 bug,是给整个应用定一条契约,再用它去检查每张卡。**

## 契约(四条,新代码一律遵守)

1. **每个用户动作必须在 300ms 内产生可见变化** —— 三选一:结果 / 进行中 / 失败原因。
   **"没有反应"本身就是 bug,不需要单独立项。**
2. **状态不许自称,必须由事实推出。** 「已就绪」必须对应磁盘上真实存在的文件;
   「已同步」必须对应本次真的推了 N 条。**推不出来就显示"未知"**,不许乐观默认。
3. **失败必须给出口。** 只说原因不够,要给"下一步能点什么"
   (重新生成 / 去配置 / 选择目录 / 重试)。
4. **正在做什么要说出来。** 耗时操作(扫描/迁移/同步/下载)必须显示范围与进度
   ("正在扫描 F:/hf_cache …"),不许只有一个转圈或者干脆无声。

## 把整类问题变成一道门禁(比逐个修更重要)

新增 `ui:no-silent-action` 冒烟:遍历主要视图里所有 `button`,逐个 click,
断言**每次点击后 300ms 内**发生下列之一 —— DOM 有变化 / 出现 toast / 出现错误条 /
路由变化。**没有任何变化的按钮直接门禁失败。**

这一道能同时抓住 M1-b(译本展开)、M2(开始复习)、M5(更改书库位置)、M4-1(空对话框),
以及**以后所有同类**。**它比这四张卡加起来更值钱** —— 前面八轮反复出现"点了没反应",
每次都是人工发现的。

例外清单(确实不该有反馈的按钮)必须显式写在测试里并注明理由,不许默默跳过。

# M1(P0)成品缺失的红卡与译本展开 —— 两个确凿根因

## M1-a 书卡的 `pack_state` 根本没被附加

`src-tauri/src/commands/library.rs` 的 `library_list`:books 分支里
`attach_pack_state(&mut x)` 只作用于**嵌套的 edition (`x`)**,循环结束直接
`out.push(v)` —— **book 对象 `v` 从头到尾没有 `pack_state` 字段**。

前端 `reader/views/library_view.js:287` 判的是 `book.pack_state`:
```js
if (book.pack_state && book.pack_state !== 'ok') { ...红卡... }
```
`undefined` → 条件为假 → 红卡永远不渲染 → 书卡照旧「已就绪 · 20 章」。

**修**:book 的 `pack_state` 由其 editions 聚合得出(**不能直接对 book 调
`attach_pack_state`** —— 原书 `pack_dir` 本来就是空的,那样会把两本未处理的书也判成
"缺失")。规则:
- 该 book 没有任何 edition → 不设 `pack_state`(未处理书,与本功能无关)
- 有 edition 且**全部** `ok` → `ok`
- 有 edition 且**任一** `missing`/`incomplete` → 取最坏值,书卡标红,
  **同时状态徽章不许再显示「已就绪」**(现在徽章来自 `book.status`,要被 `pack_state` 覆盖)

## M1-b 译本折叠切错了元素

`library_view.js:330-336`:
```js
const toggle = el('button', 'edition-toggle', `译本 (N) ▾`);
toggle.onclick = () => {
  const collapsed = editions.classList.toggle('collapsed');  // ← 切外层容器
  toggle.textContent = ...;                                   // ← 箭头会变
};
editions.appendChild(toggle);
const body = el('div', 'edition-body collapsed');             // ← 真正藏内容的是它
```
点击切的是 `editions` 容器,而内容在 `body` 上带着 `collapsed` **从不改变** →
箭头变了、内容永远展不开。用户看到的就是"点了没反应"。

**修**:toggle 切 `body.classList`。
**断言**(按教训 8):点击 `.edition-toggle` → `.edition-body` 不含 `collapsed`;
再点 → 含。**断言 DOM 类名,不是断言函数被调。**

## M1-c 缺失时的交互必须有出口

红卡上的「重新生成译本」「移除这个译本记录」已经写好了(`library_view.js:448/463`),
M1-a/M1-b 修好后它们才可见。验收要覆盖:点「重新生成译本」→ 走创建译本流程且预填源 EPUB
(`books.source_path` 实测仍在);点「移除这个译本记录」→ 只删 DB 行。

**M1 验收**:真实 DB(`%APPDATA%\aidulc\data.db`,edition `job-1786205609337-11852-1`
的 `pack_dir` 已不存在)下打开书库 → 该书卡**红色「成品文件缺失」**、徽章不再是「已就绪」;
点「译本 (1)」→ 展开并显示红色子卡与两个出口。截图入报告。

# M4(P0-)模型与依赖:按用户的三个问题重做

**用户对这一页的完整诉求(原话)**:「我就是来看一下**我需要下载什么**,然后**有没有更新**,
然后**我是不是可以把我现有的模型并进去**。」**没有的东西就不加**(空按钮比没按钮更糟)。

这一页现在三个问题一个都答不好。下面按问题拆。

## M4-1「我需要下载什么」——没有下载源的就不要放按钮

`models_view.js` 的 `DOWNLOAD_CATALOG` **只有 llm(Qwen3-4B)与 tts(Kokoro-82M)两条**,
没有任何 nlp 条目。L4 把标签从"语音识别"改成"分词 / NLP"是对的,但**「去下载」按钮的
目录数据没跟着补**,点开就是空对话框。

**修**:分词 / NLP 段**去掉「去下载」**(它有内置兜底,界面已写"不影响阅读"),
只留说明 + 「扫描已有」/「添加自定义模型」。
**通用规则:某功能没有可下载的目录项 → 不渲染下载按钮,而不是渲染一个空的。**

同时回答"我现在用的分词是什么":查 `prep/aidulc_prep/pipeline/nlp` 的实际实现,
把**当前生效方案**写在这一段(如"内置规则兜底"或"spaCy en_core_web_sm")。
用户现在完全不知道自己在用什么。

## M4-2「有没有更新」——没有渠道就说清没有,并给替换办法

J3 已经做到"无更新渠道的老实写无更新渠道",这条**保持**。补一点:
本地文件类模型标注"无更新渠道"时,要给一句**可操作的话**
(如"要换新版:下载后用「添加自定义模型」指向新文件,再设为推荐"),
否则用户知道了"没渠道"也不知道下一步干什么。

## M4-3「把我现有的模型并进去」——扫描现在是个黑盒,而且会误判

这是本卡的重头。`models_view.js:428 _scanAndRegister()` 现状有五个问题,逐条改:

**① 扫描路径不可见,且只扫一个目录**
扫描目录 = 当前 LLM 模型文件所在目录(`llm_model` 去掉文件名)。用户根本不知道扫了哪。
→ 页面上**显式列出"扫描路径"**,默认包含:模型目录、`HF_HOME`/HF 缓存
(用户实测模型在 `F:/hf_cache`,且 Kokoro 在 `hub/models--.../snapshots/...` 深层),
**允许用户增删路径**,并确认 `scan_model_dir` 对 HF 缓存布局是**递归**的。

**② 没配 LLM 时 fallback 是 `'C:/'`——会扫整个系统盘**
```js
return AiduModelService.scan(dir || 'C:/');
```
新用户(还没配模型,正是最需要扫描的人)一点扫描就遍历整个 C 盘,可能卡很久。
**必须去掉这个兜底**,改成"没有已知目录 → 让用户选一个目录"。

**③ 家族判定是二元的,把非 TTS 全判成 TTS**
```js
family: m.file_name.endsWith('.gguf') ? 'llm' : 'tts'
```
**这解释了截图里的怪现象**:「语音合成」段下挂着 `pytorch_model`、
`ggml-silero-v5.1.2`(VAD)、`ggml-large-v3`(whisper)——它们都不是 TTS,
只是"不以 .gguf 结尾"就被塞进去了。
→ 按文件名/目录特征识别(kokoro→tts、ggml-large/whisper→asr 或"未识别"、
silero→vad、`.gguf`→llm、spaCy 目录→nlp),**识别不出的一律标「未识别」让用户自己选家族,
不许瞎猜**。已经被误登记的存量条目要能改家族或移除。

**④ 扫到就全部自动登记,用户没有确认机会**
现状 `found.map(register)` 直接全登记。
→ 改成**先列出候选**(路径 / 大小 / 推测家族 / 是否已登记),用户勾选后再登记。

**⑤ 扫描 0 结果只有一句 toast,没有下一步**
→ 无结果时给明确操作:「在这些路径下没找到模型:<列出路径>。你的模型在别处?
【选择目录扫描…】或【添加自定义模型】」。**这正是用户说的"缺少扫描,需要如何操作"。**

## M4 验收

# M3(**移出本轮**)后端 × 主体 的对应关系

**决定:本轮不做,理由如下。设计结论先记在这里,等前置条件满足再执行。**

1. **前置条件没满足**:M0 之前,手机端**一次都没成功同步过**。在"单后端还没跑通"
   的情况下改成多后端矩阵,等于在没验证的地基上加层。
2. **风险与收益不匹配**:它要改 `sync_state` 主键(单主键 → 复合主键)和凭据存储的 key
   结构 —— 是本轮最危险的两处改动;而收益是一个**当前只有一个后端的用户**用不到的能力。
   我们刚在数据迁移上丢过 991 MB,不该在同一轮里再动一次存储层。
3. **触发条件**:等 ① M0 落地且手机端实测能拉到词 ② 用户确实要接第二个后端
   (家里 VPS + 自己的 CF,或给家人开第三个位置)时再做。

**设计结论(留档,执行时照此做,不要重新讨论)**:

用户的问题很准:「这个位置和对应的数据 profile 的主体对应关系是怎么对应的?
一次同步 2 个位置吗?还是勾选是否同步?」

**先厘清三个概念(界面上也要这么说人话)**:
- **主体 / user**(顶栏的「我」)= 谁的词库。本地概念。
- **后端 / backend** = 词库同步到哪台服务器。
- **token** = 某个主体在某个后端上的凭据。**它天然是 (主体 × 后端) 的交叉物**。

**现状的问题**:`credentials.rs::save_cf_token_for(user_id, ...)` 只按 **user** 存 token,
不含后端维度;`sync_state` 主键也只有 `user_id`。所以"一个主体连多个后端"在存储层
**根本表达不了** —— UX3 的 L11 加了后端列表,但底下的账还是一本。

**定下来的模型(按用户描述)**:
- 关系是**矩阵**:每个 (主体, 后端) 一格,格子里有 `token` + `是否启用同步`。
- 一个主体**可以同时启用多个后端**(如"我"同时推家里 VPS 和自己的 CF)。
  同步 = 对当前主体所有**已启用**的后端依次先推后拉;冲突照旧 `updated_at` 新者胜。
- 新成员("第三个位置就是新人的")= 新建本地 user → 在他自己选的后端上用邀请码换 token。
  **绝不复用别人的 token**(这条老规矩不变)。

**必要的存储改动(这是本卡的主体工作,单独提交)**:
- `sync_state` 主键 `user_id` → **复合主键 `(user_id, endpoint_key)`**。迁移:
  老行按当前 `endpoint_key` 落一行。
- `credentials` 的 token key 从 `user_id` → `user_id + endpoint`。
  **动凭据存储前先写迁移方案**:老 key 读得到就迁,迁不动要能明确报错而不是静默丢失同步能力。
- 设置页:后端列表每项加**「同步此后端」勾选**,并显示这一格属于**哪个主体**
  (当前主体的视角),让"谁的库同步到哪"一眼可见。

**验收**:同一主体启用两个后端 → 一次「立即同步」两边都收到(各自给出推 N 条);
取消勾选其一 → 只推另一个;切主体后看到的是该主体自己的后端启用状态。
