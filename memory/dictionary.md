# aidulc 项目记忆 — 词典/查词 (2026-09-04)

按全局 CLAUDE.md 框架记录查词维度现状、权衡、坑。以实测为准。

## 系统构成

- 三层查词(`commands/dictionary.rs::word_lookup`): 个人缓存(`dictionary` 表, 含语境例句)
  → 全局词典基底(`dict_base` 表, 只有稳定字段, 瞬时不占显卡) → 本地 LLM 兜底
  (`infrastructure/dict_daemon.rs`, 侧车常驻守护, 懒启动/120s 空闲回收)。未配置 LLM
  或侧车调用失败都不报错、给占位释义——本地词典本来就是主力, LLM 是锦上添花,
  不该是单点故障(2026-09-04 审计确认此前就已如此, 不是这轮新加的)。
- 词典基底种子: ECDICT(MIT, `resources/dict_seed.jsonl`, `include_str!` 编进二进制) 按
  Collins 星级/考试标签过滤出的 19139 条核心词, 不是全量 77 万条; 生成过滤子集的
  `build_seed.py` 是一次性脚本, **没有留在仓库里**——想扩大种子覆盖面得重写这个脚本。
- 本地 LLM 结果自动反哺基底(`dictionary_service::persist_llm` 里 `upsert_if_absent`,
  first-write-wins), 在线 AI 结果**不会**——见下面"三来源写入策略"。

## 关键决策与权衡

1. **词典基底 vs 本地 LLM 不是互斥的两套, 是"基底=LLM 结果的持续增长缓存层"**:
   查得越多基底越厚实, 后面任何人查同一个词都不用再跑一次 LLM。first-write-wins
   (不覆盖已有词条)是为了避免不同来源反复互改造成 churn, 代价是"基底一旦定型,
   纠错只能靠专门的覆盖通道"(见下条)。

2. **三来源写入策略(2026-09-04 用户拍板)**:
   - 本地 LLM → 写个人缓存(`dictionary`) + 合并进共享基底(`dict_base`, upsert_if_absent)。
   - 在线 AI → **只写个人缓存, 绝不碰共享基底**。理由: 在线结果来自用户自己配置的
     付费引擎, 没有审核机制, 如果直接覆盖/合并进全体共用的 `dict_base`, 一次可能
     出错的在线查询就会静默污染这台机器上其他人/其他档案看到的默认答案。个人缓存
     用 `DictRepo::upsert`(ON CONFLICT DO UPDATE)天然支持"纠正"语义, 不需要另开
     一条允许覆盖共享表的通道。
   - 面板给了显式确认步骤(「存入我的词典」按钮), 不自动落库——查完不代表用户
     认可这个答案。
   - 用户原始诉求是"三个来源查完都汇总回词典", 上面这版是权衡过写入范围后的
     折中(拍板记录见对话, 不是我单方面简化)。

3. **本地 AI 重查按钮改成常驻, 不再只在基底命中时出现**(2026-09-04): 之前只有
   `source==='base'` 才显示"结合这句话再讲一下"。用户诉求: 不管当前显示哪一层
   结果都该能重新跑一次本地 LLM, 因为模型可能被用户换了新版本, 同一个词换个
   模型可能给出不同/更好的答案。按钮语义从"基底缺例句时补全"扩成"随时可以让
   本地模型再试一次", 文案也统一成「用本地 AI 再查一次」。

4. **查词失败恢复: 强制重置 + 显卡占用检测复用**(2026-09-04, 起因是用户报告"本地
   模型没拉起来, 没有检查/重置按钮"): `dict_daemon::stop()` 早就存在且幂等, 但从
   没有 Tauri command 把它暴露给前端——查词失败只能等 30s `LOOKUP_TIMEOUT` 被动
   检测到挂死才清注册表。加了 `dict_daemon_reset` command, 面板报错时点按钮立即
   强杀重建, 不用等超时。另外"模型被占用"最常见的真实根因是显卡被外部进程(用户
   自己起的 llama-server.exe 之类)占着——这个检测(`gpu_status`/`gpu_kill_process`)
   **早就写好了**, 但只接在"打开书"那个流程里, 查词失败面板看不到也点不到。这次
   复用同一对 command, 查词失败时也顺带查一次, 命中就给"关闭占用进程并重试"。
   **教训**: 加新功能前先搜一遍现有 command, 这次两处能力(reset/gpu 检测)都是
   "已经实现但没接线"的典型例子, 不是从零写的。

5. **多词典源管理为什么拆成两个 repo 文件**(2026-09-04): `dict_base_import_file`
   早就支持导入 JSONL/CSV(2026-08-21 做的), 但所有导入词条混进同一个笼统的
   'custom' 桶, 删不掉某一批。加 `dict_base_sources` 表(文件名/标签/词数/时间)+
   `dict_base.source_id` 列后, `dict_base_repo.rs` 单文件涨到 650+ 行, 撞了
   `scripts/file_size_baseline.json` 的 600 行默认硬上限。**没有走"登记豁免"这条
   路**, 而是把 `dict_base_sources` 表自身的 record/list/delete 拆到新文件
   `dict_base_sources_repo.rs`——这不违反"每张表一个写者": `dict_base_sources`
   表本来就只有这一个文件写, `dict_base` 表的删除(`DELETE FROM dict_base WHERE
   source_id=?`)仍然留在 `dict_base_repo.rs` 里, 两张表各自单一写者没变, 只是
   "记一批导入" 和 "存词条本身" 这两件独立的事分了文件。**登记豁免 vs 拆文件怎么
   选**: 豁免要求"拆分会更糟"(破坏事务原子性/顺序审计/脚本路径耦合), 这次没有
   那三条理由, 硬撑理由等于"图省事", 所以选择真拆。

## 已知缺口 / 未做的事

- **MDX 格式导入没做**(2026-09-04 调研, 未落地): 用户想直接导入朗文/牛津这类商业
  词典的原始发行格式 `.mdx`(欧路词典/GoldenDict 用的私有二进制格式, 无官方规范,
  社区靠反编译还原, 版本 1.2/2.0/3.0 压缩方式不同——无压缩/LZO/zlib, 部分还加密)。
  查过 Rust 生态里能解析它的 crate(`opendict-rs`/`mdict-parser`/`readmdict`/
  `dictutils`), **全部是个人业余项目级别**: 下载量几十到三千, star 数 0-20,
  `opendict-rs`(最新、API 最全)只有 5 次提交、0 star; `mdict-parser`(相对成熟)
  README 自己说 v3/mdd/加密词典都没实现。按"先实测再下结论"原则, 没有在没验证过
  真实 .mdx 文件之前就把这类依赖接进生产代码。**如果以后要做**: 先拿用户手头
  真实的 .mdx 文件跑一遍 spike 脚本验证能不能解出来, 再决定要不要接。当前的
  导入口子(JSONL/CSV)是我们自己定义的简单格式, 只能吃已经转换过的数据。
- 词典基底种子只有 19139 条(ECDICT 全量的一个子集), 不是"查不到词"的 bug, 是
  故意过滤的结果。想扩大覆盖面最低风险的路径是重新生成/放宽这个过滤(仍是 MIT
  协议, 无版权问题), 比啃 MDX 格式便宜得多——这条建议给过用户, 还没决定要不要做。
